Деініціалізація

deinit: коли викликається, що в ньому можна робити, і як він співвідноситься з фіналізаторами та IDisposable у C#.

У книзі: deinitialization

Як працює деініціалізація

Деініціалізатор викликається безпосередньо перед звільненням екземпляра класу. Є лише в класах (і в noncopyable-структурах, про які згадаємо в уроці про узагальнення).

Swift
final class FileHandleBox {
    let path: String
    init(path: String) {
        self.path = path
        print("Відкрито \(path)")
    }
    deinit {
        print("Закрито \(path)")
    }
}

Правила:

  • deinit у класу може бути лише один, без параметрів і без дужок.
  • Його викликають автоматично. Викликати вручну не можна.
  • Деініціалізатор суперкласу успадковується і викликається автоматично після деініціалізатора підкласу, навіть якщо підклас свого не має.
  • У deinit екземпляр ще живий: можна читати й змінювати будь-які властивості.

Пам'ять звільняє ARC (урок 26). Тому deinit викликається детерміновано: коли зникає останнє сильне посилання. Зверни увагу: «останнє посилання» — це останнє використання, а не обов'язково кінець області видимості. В оптимізованій збірці об'єкт може звільнитися одразу після останнього звернення до нього. Якщо потрібно гарантовано утримати об'єкт до певного місця, є withExtendedLifetime(_:_:).

Деініціалізатор у дії

Типовий випадок — об'єкт, що підписується на щось у init і відписується в deinit. Тоді підписка живе рівно стільки, скільки живе об'єкт:

Swift
import Foundation

final class ThemeObserver {
    private var token: NSObjectProtocol?

    init(onChange: @escaping @Sendable () -> Void) {
        token = NotificationCenter.default.addObserver(
            forName: .themeDidChange, object: nil, queue: .main
        ) { _ in onChange() }
        print("Підписка створена")
    }

    deinit {
        if let token { NotificationCenter.default.removeObserver(token) }
        print("Підписка знята")
    }
}

extension Notification.Name {
    static let themeDidChange = Notification.Name("themeDidChange")
}

var observer: ThemeObserver? = ThemeObserver { print("Тема змінилась") }
observer = nil      // deinit одразу: "Підписка знята"

Присвоєння nil прибрало останнє посилання, і deinit виконався негайно. Якби на той самий об'єкт посилалась ще одна змінна, він жив би далі.

C#

Фіналізатор ~ClassName() у C# викликає GC колись потім, а для детермінованого звільнення ресурсів існує IDisposable і using. У Swift deinit поєднує обидві ролі: він і автоматичний, і детермінований. Тому патерн «закрити ресурс у deinit» тут нормальний. Обережно лише з циклами посилань: якщо вони є, deinit не викличеться ніколи.

Пастка

Якщо deinit не викликається, коли ти очікуєш, — у 90% випадків десь є цикл сильних посилань, найчастіше через замикання, що захопило self. Перевіряй це в Memory Graph Debugger у Xcode.

Перевір себе

Обери відповідь — одразу побачиш, чи правильно, і пояснення.

1. Коли викликається deinit?

Пам'ять звільняє ARC, тож deinit спрацьовує детерміновано — після останнього використання об'єкта.

2. У яких типів є deinit?

Звичайні структури й enum копіюються як значення, тож моменту «знищення» в них немає.

3. Ти закрив екран, а print у його deinit не з'явився. Найімовірніша причина?

Якщо об'єкт хтось тримає сильно (часто по колу), його лічильник не падає до нуля, і deinit не викликається.

4. Що з цього — аналог deinit у C#?

Тому в Swift нормально звільняти ресурси (відписки, файли) прямо в deinit.

Практика
  1. Зроби клас AudioSession з print у init і deinit. Створи його в локальній змінній функції й простеж, коли спрацьовує deinit у Debug і в Release.
  2. Створи дві змінні, що посилаються на один екземпляр. Обнули їх по черзі й простеж момент виклику deinit.
  3. Зроби підклас з власним deinit і переконайся, в якому порядку викликаються деініціалізатори підкласу й суперкласу.
