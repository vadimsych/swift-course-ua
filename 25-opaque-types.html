Непрозорі й упаковані типи

some Protocol і any Protocol: що це, чим відрізняються, коли що використовувати, і як some у параметрах замінює generic-синтаксис.

У книзі: opaquetypes

Звідки береться проблема

Generic-код у Swift зберігає точні типи — і це добре для продуктивності, але погано для сигнатур. Подивись, який тип має звичайний ланцюжок ледачих операцій:

Swift
let prices = [199, 49, 99, 0, 299]

let premium = prices.lazy
    .filter { $0 > 0 }
    .map { Double($0) * 0.8 }

// тип premium:
// LazyMapSequence<LazyFilterSequence<LazySequence<[Int]>.Elements>, Double>

Якщо загорнути цей ланцюжок у функцію й написати тип результату явно, деталі реалізації стануть частиною API: змінив filter на prefix — змінився тип, і всі, хто використовує функцію, мусять перекомпілюватися або ламаються.

Повернення непрозорого типу

some Sequence<Double> означає: «функція повертає один конкретний тип, що відповідає Sequence з елементами Double, але я не кажу який».

Swift
func discountedPrices(_ prices: [Int]) -> some Sequence<Double> {
    prices.lazy
        .filter { $0 > 0 }
        .map { Double($0) * 0.8 }
}

for p in discountedPrices([199, 0, 99]) {
    print(p)        // ≈159.2, ≈79.2
}

Порівняй, хто обирає конкретний тип:

  • generic <T: Sequence>: конкретний тип обирає той, хто викликає;
  • some Sequence у результаті: конкретний тип обирає реалізація, а викликач бачить лише протокол.

Компілятор при цьому знає справжній тип: немає накладних витрат, а асоційовані типи протоколу (як Element) лишаються відомими. Тому for p in ... вище знає, що p — Double.

Головне правило: усі шляхи повернення мають давати той самий конкретний тип:

Swift
func prices(onlyPaid: Bool, _ all: [Int]) -> some Sequence<Int> {
    if onlyPaid {
        return all.filter { $0 > 0 }      // [Int]
    }
    return all.lazy                       // помилка: LazySequence<[Int]> — інший тип
}

Виправити можна, звівши обидві гілки до одного типу (тут — повертати [Int] в обох), або повернути упакований тип any Sequence<Int>.

Конкретний тип може залежати від generic-параметра — правило «один тип» від цього не порушується, бо для кожного T це один і той самий тип:

Swift
func pairwise<T>(_ items: [T]) -> some Sequence<(T, T)> {
    zip(items, items.dropFirst())       // завжди Zip2Sequence<[T], ArraySlice<T>>
}

for (prev, next) in pairwise([3, 7, 12]) {
    print(next - prev)   // 4, 5 — типи елементів відомі компілятору
}

Непрозорий тип не можна використовувати у вимогах протоколу і всередині функціональних типів параметрів. А метод класу з результатом some P скомпілюється, але перевизначити його в підкласі не вийде — у підкласу був би інший прихований тип.

Порада

Найвідоміший приклад — var body: some View у SwiftUI. Справжній тип body — гігантський вкладений generic-тип, який компілятор знає, а ти не мусиш писати.

Упаковані протокольні типи

any P — це «коробка» (existential), в якій може лежати будь-яке значення, що відповідає протоколу, причому різні значення можуть мати різні типи. Візьмемо знижки:

Swift
protocol Discount {
    func apply(to price: Decimal) -> Decimal
}

struct Percent: Discount {
    let value: Decimal
    func apply(to price: Decimal) -> Decimal { price * (1 - value / 100) }
}

struct Fixed: Discount {
    let amount: Decimal
    func apply(to price: Decimal) -> Decimal { max(0, price - amount) }
}

// конфіг з сервера: різні типи знижок в одному масиві
var activeDiscounts: [any Discount] = [Percent(value: 20), Fixed(amount: 10)]

func discount(for code: String) -> any Discount {
    code.hasPrefix("FIX") ? Fixed(amount: 50) : Percent(value: 10)   // різні типи — ок
}

Ціна гнучкості:

  • значення зберігається в коробці, великі значення — в купі;
  • виклики методів ідуть через динамічну диспетчеризацію;
  • компілятор не знає конкретного типу, тож для протоколів з асоційованими типами чи Self-вимогами частина можливостей недоступна напряму.

Щоб отримати з коробки конкретний тип, можна привести через as? або передати значення в generic-функцію — Swift автоматично «відкриє коробку»:

Swift
func finalPrice<D: Discount>(_ d: D, base: Decimal) -> Decimal { d.apply(to: base) }

let boxed: any Discount = Percent(value: 15)
finalPrice(boxed, base: 200)     // D виведено як Percent

any Any і any AnyObject нічого не змінюють — ці типи й так «коробки».

Три способи зберігати «щось, що відповідає протоколу»

Swift
struct Checkout1<D: Discount> { var discounts: [D] }   // generic: усі одного типу, тип обирає той, хто створює
struct Checkout2 { var discounts: [any Discount] }     // упакований: різні типи впереміш
func checkout3(_ discounts: [some Discount]) { }       // непрозорий параметр: усі одного типу, як у варіанті 1

Різниця між some і any

some P any P
Хто знає конкретний тип компілятор тільки рантайм
Різні типи в різних місцях ні, один тип так
Різнорідні колекції ні так, [any P]
Вартість як у конкретного типу коробка + динамічні виклики
Асоційовані типи й Self зберігаються обмежено

Особливо помітна різниця з Equatable:

Swift
func makeID() -> some Equatable { 42 }
let a = makeID(), b = makeID()
a == b                                  // ок: компілятор знає, що це той самий тип

let x: any Equatable = 42
let y: any Equatable = "42"
// x == y                               // помилка: типи можуть бути різні
Порада

Правило вибору: за замовчуванням some (або generics), any — коли справді треба зберігати різні типи разом чи змінювати тип під час виконання.

C#

any P — це звичайне використання інтерфейсу як типу в C#, з боксингом для структур. Аналога some P у C# немає: найближче — повертати конкретний тип, але приховати його неможливо.

Непрозорі типи параметрів

some у позиції параметра — скорочений запис generic-функції:

Swift
func preview(_ d: some Discount) -> Decimal {
    d.apply(to: 100)
}
// те саме, що:
func preview2<D: Discount>(_ d: D) -> Decimal {
    d.apply(to: 100)
}

Правила:

  • кожен параметр some — окремий параметр типу, тому func compare(_ a: some Equatable, _ b: some Equatable) приймає два різні типи, і a == b не скомпілюється;
  • до some не можна додати where чи вимогу рівності типів — для цього повертайся до явного <T: P> з where;
  • some можна використовувати в параметрах функцій, ініціалізаторів і сабскриптів, комбінувати з & і вкладати в інші типи: [some Discount].

Перевір себе

Обери відповідь — одразу побачиш, чи правильно, і пояснення.

1. Чому погано писати в результаті функції явний тип на кшталт LazyMapSequence<LazyFilterSequence<...>, Double>?

Точний generic-тип відображає кожен крок ланцюжка, тож будь-яка зміна реалізації ламає сигнатуру.

2. Хто обирає конкретний тип у функції func discounted() -> some Sequence<Double>?

У generic-параметра тип обирає викликач, а в непрозорого результату — реалізація.

3. Чому тут помилка компіляції?

Swift
func numbers(_ unique: Bool) -> some Sequence<Int> {
    if unique {
        return Set([1, 2])
    }
    return [1, 2]
}

print(Array(numbers(true)).count)

Усі шляхи повернення з some мають давати один і той самий конкретний тип.

4. Що надрукує цей код?

Swift
func evens() -> some Sequence<Int> {
    (1...6).lazy.filter { $0 % 2 == 0 }
}

for x in evens() {
    print(x * 10)
}

Компілятор знає, що елементи — Int, тож x * 10 працює. Фільтр лишає парні 2, 4, 6.

5. Що надрукує цей код?

Swift
protocol Discount {
    func apply(to price: Int) -> Int
}

struct Percent: Discount {
    let value: Int
    func apply(to price: Int) -> Int { price * (100 - value) / 100 }
}

struct Fixed: Discount {
    let amount: Int
    func apply(to price: Int) -> Int { max(0, price - amount) }
}

func run() {
    let discounts: [any Discount] = [Percent(value: 50), Fixed(amount: 10)]
    var price = 200
    for d in discounts {
        price = d.apply(to: price)
    }
    print(price)
}
run()

[any Discount] тримає знижки різних типів. Спершу 50% від 200 — 100, потім мінус 10 — 90.

6. Яке твердження про any P неправильне?

Конкретний тип у коробці відомий лише під час виконання. Саме тому any гнучкий, але дорожчий.

7. Що надрукує цей код?

Swift
protocol Discount {
    func apply(to price: Int) -> Int
}

struct Fixed: Discount {
    let amount: Int
    func apply(to price: Int) -> Int { price - amount }
}

func typeName<D: Discount>(_ d: D) -> String {
    "\(D.self)"
}

let boxed: any Discount = Fixed(amount: 5)
print(typeName(boxed))

Swift автоматично відкриває коробку при передачі в generic-функцію, і D стає справжнім типом Fixed.

8. Чим struct Checkout<D: Discount> { var discounts: [D] } відрізняється від struct Checkout { var discounts: [any Discount] }?

Generic фіксує один тип D для всього масиву. [any Discount] тримає різні типи.

9. Чому тут помилка компіляції?

Swift
let x: any Equatable = 1
let y: any Equatable = 2
print(x == y)

== вимагає двох значень одного типу, а компілятор не знає, що лежить у кожній коробці.

10. Що надрукує цей код?

Swift
func makeID() -> some Equatable {
    42
}

print(makeID() == makeID())

Обидва виклики повертають той самий прихований тип, і компілятор це знає, тож == дозволений.

11. Чому тут помилка компіляції?

Swift
func same(_ a: some Equatable, _ b: some Equatable) -> Bool {
    a == b
}

print(same(1, 1))

Це те саме, що <A: Equatable, B: Equatable>. Для одного типу потрібен явний <T: Equatable>.

12. Що неможливо зробити з some у параметрі, але можливо з явним <T: P>?

До some не можна додати where. Для таких вимог повертаються до явного generic-синтаксису.

Практика
  1. Напиши функцію blackFridayDiscount() -> some Discount, що повертає комбінацію знижок (зроби generic-тип Combined<A, B>).
  2. Спробуй повернути з неї різні типи в різних гілках if. Виправ двома способами: зведенням до одного типу і через any.
  3. Збережи в масиві [any Discount] знижки з конфігу і застосуй їх по черзі.
  4. Перепиши generic-функцію з попереднього уроку з використанням some у параметрах. Де це неможливо?
