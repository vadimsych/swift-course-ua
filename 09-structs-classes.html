Структури й класи

Чим відрізняються struct і class у Swift, що таке value semantics, memberwise-ініціалізатори, оператори тотожності і як обирати між ними — з погляду C#-розробника.

У книзі: classesandstructures

Те саме слово, інша роль

У C# struct — нішевий інструмент для дрібних даних, і майже все пишуть класами. У Swift навпаки: Int, String, Array, Dictionary, Date, URL — структури, а класи потрібні лише там, де без них не обійтись.

C# struct Swift struct Swift class
Семантика значення значення посилання
Методи, властивості, ініціалізатори так так так
Розширення й протоколи (інтерфейси) інтерфейси — так так так
Успадкування ні ні так
Деструктор ні ні (крім noncopyable) deinit
Хто може змінювати поля будь-який метод лише mutating-методи будь-який метод
Типова роль дрібні дані майже все: моделі, стани, конфіги сервіси, спільний стан, UIKit

Чому в Swift перевага на боці структур: значення, яке ніхто інший не може змінити у тебе за спиною, простіше аналізувати, безпечніше передавати між потоками (урок 18) і дешевше в пам'яті — без лічильника посилань. Клас вартий своєї складності, коли потрібне одне з трьох: тотожність (саме цей об'єкт, а не його копія), успадкування або сумісність з Objective-C API.

Оголошення й створення

Swift
import Foundation

struct Money {
    var amount: Decimal
    var currency = "UAH"
}

final class Wallet {
    private(set) var history: [Money] = []
    func deposit(_ m: Money) { history.append(m) }
}

Імена типів — у UpperCamelCase, властивостей і методів — у lowerCamelCase. Звертання до властивостей — через крапку.

Структура отримує memberwise-ініціалізатор автоматично: параметр для кожної збереженої властивості, а для властивостей зі значенням за замовчуванням — необов'язковий. Клас такого не отримує — йому дістається лише init() без параметрів, якщо всі властивості мають початкові значення.

Swift
let price = Money(amount: 199)                     // currency = "UAH"
let fee = Money(amount: 2.5, currency: "USD")
let wallet = Wallet()
wallet.deposit(price)
Пастка

Memberwise-ініціалізатор зникає, щойно в самому оголошенні структури з'являється власний init. Щоб зберегти обидва, власні ініціалізатори пишуть у extension (урок 14).

Value semantics на практиці

Найкраще різницю видно на типовому баґу «редагування копії». Уяви екран, що редагує налаштування профілю:

Swift
struct ProfileSettings {
    var nickname: String
    var notificationsOn: Bool
}

final class ProfileStore {
    var settings = ProfileSettings(nickname: "guest", notificationsOn: true)
}

let store = ProfileStore()

var draft = store.settings          // копія: форма редагує чернетку
draft.nickname = "neo"
print(store.settings.nickname)      // "guest" — збережене не змінилось

store.settings = draft              // зберегли явно, коли користувач натиснув «Зберегти»

Для форми редагування це саме те, що треба. У C# з класом ProfileSettings змінна draft була б тим самим об'єктом, і форма змінювала б збережені дані одразу.

Що ще випливає з value semantics:

  • копія створюється при присвоєнні, передачі у функцію і збереженні у властивість; стандартні колекції копіюють буфер лише при першій зміні (copy-on-write), тож це дешево;
  • let зі структурою заморожує все значення, навіть var-властивості: let s = store.settings; s.nickname = "x" не скомпілюється;
  • enum — теж value type з тими самими правилами.

Reference semantics

Змінна класу зберігає посилання. Присвоєння, передача у функцію чи збереження в колекції копіюють посилання, а не об'єкт, тож зміну видно звідусіль:

Swift
let shared = ProfileStore()
var observers = [shared]            // масив тримає те саме посилання
observers[0].settings.nickname = "trinity"
print(shared.settings.nickname)     // "trinity"

let shared — константа, але властивості об'єкта змінюються: let фіксує лише посилання.

Пастка

Структура, що містить поле-клас, при копіюванні копіює лише посилання на нього. Справжня value semantics тримається, тільки якщо всі поля структури самі є value types.

Тотожність: === і !==

=== перевіряє, чи дві змінні вказують на той самий екземпляр класу (аналог ReferenceEquals). == — рівність за значенням, і для класу вона існує лише тоді, коли клас реалізує Equatable.

Swift
if observers[0] === shared { print("Той самий об'єкт") }

А де вказівники?

Для звичайного коду вони не потрібні: посилання на об'єкти класів працюють без жодного спеціального синтаксису. Ручна робота з адресами пам'яті можлива через типи UnsafePointer і подібні, але це інструмент для інтеропу з C і рідкісних оптимізацій.

Актори

Третій вид reference types — актори (урок 18): схожі на класи, але захищають свій змінюваний стан від одночасного доступу з різних задач.

Як обрати

Питання struct class
Дані, які достатньо порівнювати за значенням (гроші, налаштування, DTO з API) ✓
Потрібна тотожність: «той самий» сервіс, сесія, кеш, з'єднання ✓
Потрібне успадкування (наприклад, підклас UIViewController) ✓
Потрібен deinit для звільнення ресурсу ✓ (або ~Copyable struct)
Модель для SwiftUI-View ✓
Спостережувана модель стану (@Observable) ✓
Порада

Класи в Swift зазвичай позначають final, якщо успадкування не планується. Це прибирає динамічну диспетчеризацію і робить намір явним.

Перевір себе

Обери відповідь — одразу побачиш, чи правильно, і пояснення.

1. Що з цього вміє лише клас, а структура — ні?

Наслідування й підрахунок посилань — лише в класів.

2. Що за типом є Array, String і Dictionary у Swift?

Стандартна бібліотека майже повністю складається зі структур.

3. Що отримує структура автоматично, а клас — ні?

Класу ініціалізатор з параметрами доведеться написати вручну.

4. Що надрукує цей код?

Swift
struct Settings { var nickname: String }
final class Store { var settings = Settings(nickname: "guest") }

let store = Store()
var draft = store.settings
draft.nickname = "neo"
print(store.settings.nickname)

Settings — структура, тож draft — окрема копія.

5. Що станеться з let s = Settings(nickname: "a"); s.nickname = "b", якщо Settings — структура з var nickname?

let зі структурою заморожує все значення, навіть var-властивості.

6. Що надрукує цей код?

Swift
final class Box { var value = 1 }
let a = Box()
let b = a
b.value = 5
print(a.value)

a і b посилаються на той самий об'єкт. let фіксує лише посилання.

7. Що перевіряє ===?

== — рівність за значенням, === — тотожність об'єктів.

8. У якому випадку варто обрати клас, а не структуру?

Клас потрібен, коли важлива тотожність — «той самий» об'єкт для всіх.

Практика
  1. Змоделюй кошик покупок як структуру з масивом позицій і клас CartStore, що його зберігає. Зроби «чернетку» кошика на екрані оформлення, зміни якої застосовуються лише після підтвердження.
  2. Створи структуру з полем-класом і покажи, що копія структури «ділить» об'єкт з оригіналом.
  3. Додай до Money власний init(fromCents:) так, щоб memberwise-ініціалізатор теж лишився.
  4. Для кожної сутності з твого Unity-проєкту (наприклад, PurchaseConfig, AnalyticsService, PlayerProgress) визнач: struct чи class у Swift, і чому.
