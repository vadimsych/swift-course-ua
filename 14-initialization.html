Ініціалізація

Найскладніший розділ про типи: ініціалізатори структур і класів, делегування, designated і convenience, двофазна ініціалізація, успадкування ініціалізаторів, failable і required.

У книзі: initialization

Початкові значення збережених властивостей

Головне правило: до завершення ініціалізації кожна збережена властивість мусить мати значення. Компілятор перевіряє це статично. Значення задають двома способами: у самому оголошенні або в ініціалізаторі.

C#

У C# поля автоматично отримують default: 0, null, false. У Swift значень за замовчуванням «нізвідки» немає. Неініціалізована властивість — помилка компіляції. Виняток — опціонали var, що за замовчуванням nil.

Ініціалізатори

Swift
struct Stopwatch {
    var seconds: Double
    init() {
        seconds = 0
    }
}

Присвоєння в ініціалізаторі (і значення за замовчуванням) не викликають спостерігачів властивості.

Значення за замовчуванням

Якщо властивість завжди починає з того самого значення, краще задати його в оголошенні:

Swift
struct Stopwatch {
    var seconds = 0.0
}

Так коротше, тип виводиться, і з'являється ініціалізатор за замовчуванням (нижче).

Власна ініціалізація

Параметри

Ініціалізаторів може бути кілька — з різними параметрами:

Swift
struct Avatar {
    var imageName: String
    init(imageName: String) { self.imageName = imageName }
    init(initials: String) { imageName = "initials_" + initials.prefix(2).uppercased() }
    init(level: Int) { imageName = level >= 50 ? "avatar_gold" : "avatar_basic" }
}

let a = Avatar(initials: "vs")    // imageName == "initials_VS"

Імена параметрів і мітки

У ініціалізаторів немає власного імені, як у функцій, тому їх розрізняють за мітками й типами параметрів. Через це Swift автоматично дає мітку кожному параметру ініціалізатора, і писати мітки при виклику обов'язково.

Параметри без мітки

Якщо мітка зайва, використовуй _:

Swift
struct Hex {
    var value: Int
    init(_ text: String) { value = Int(text, radix: 16) ?? 0 }
}
let color = Hex("FF8800")

Опціональні властивості

Властивість, яка може «логічно» не мати значення (зокрема відразу після ініціалізації), оголошують опціональною. Вона автоматично отримує nil:

Swift
final class Quiz {
    let question: String
    var answer: String?     // nil, поки користувач не відповів
    init(question: String) { self.question = question }
}

Константні властивості

let-властивості можна присвоїти в будь-якому місці ініціалізатора, але рівно один раз. У класах let-властивість може присвоїти лише клас, що її оголосив, а не підклас.

Ініціалізатори за замовчуванням

Якщо всі властивості структури чи класу мають значення за замовчуванням і немає власних ініціалізаторів, тип отримує init() без параметрів.

Swift
final class Session {
    var token: String?
    var retries = 0
}
let s = Session()

Memberwise-ініціалізатори структур

Структури додатково отримують ініціалізатор з параметрами для всіх збережених властивостей у порядку оголошення. Параметри для властивостей зі значеннями за замовчуванням можна пропускати:

Swift
struct Tile {
    var x = 0
    var y = 0
}
let a = Tile(x: 2, y: 3)
let b = Tile(y: 5)
let c = Tile()

Делегування ініціалізаторів у value types

Ініціалізатор може викликати інший ініціалізатор того самого типу через self.init, щоб не дублювати код. У value types це просто, бо успадкування немає.

Зручний прийом — тримати допоміжні ініціалізатори в extension: тоді делегування працює, а автоматичні memberwise-ініціалізатор і ініціалізатор за замовчуванням залишаються:

Swift
struct RetryPolicy {
    var maxAttempts = 3
    var delay = 1.0
    var multiplier = 2.0
}

extension RetryPolicy {
    init(aggressive: Bool) {
        if aggressive {
            self.init(maxAttempts: 10, delay: 0.2, multiplier: 1.5)   // делегуємо memberwise
        } else {
            self.init()                                              // і ініціалізатору за замовчуванням
        }
    }
}

let p1 = RetryPolicy()                       // автоматичний — збережено
let p2 = RetryPolicy(maxAttempts: 5)         // memberwise — збережено
let p3 = RetryPolicy(aggressive: true)       // власний, делегує

Якби init(aggressive:) стояв у самому оголошенні структури, обидва автоматичні ініціалізатори зникли б, і їх довелося б писати вручну.

Ініціалізація класів і успадкування

Усі збережені властивості класу, включно з успадкованими, мають отримати значення під час ініціалізації. Для цього в класах є два види ініціалізаторів.

Designated і convenience

  • Designated (основний) — повністю ініціалізує властивості свого класу й викликає ініціалізатор суперкласу. Кожен клас має щонайменше один.
  • Convenience (допоміжний) — для зручних варіантів створення. Він мусить зрештою викликати designated-ініціалізатор того самого класу.

Синтаксис

Swift
class Connection {
    var host: String
    var port: Int

    init(host: String, port: Int) {            // designated
        self.host = host
        self.port = port
    }

    convenience init(host: String) {           // convenience
        self.init(host: host, port: 443)
    }
}

Правила делегування в класах

  1. Designated-ініціалізатор мусить викликати designated-ініціалізатор безпосереднього суперкласу.
  2. Convenience-ініціалізатор мусить викликати інший ініціалізатор того самого класу.
  3. Convenience-ініціалізатор мусить зрештою дійти до designated.

Коротко: designated делегують вгору, convenience — вбік.

Двофазна ініціалізація

Ініціалізація класу йде у дві фази.

Фаза 1 — знизу вгору: кожен клас у ланцюжку присвоює значення своїм збереженим властивостям і передає керування ініціалізатору суперкласу. Коли базовий клас ініціалізував свої властивості, пам'ять екземпляра повністю ініціалізована.

Фаза 2 — згори вниз: кожен клас може налаштувати екземпляр далі: змінити успадковані властивості, викликати методи, використовувати self.

Компілятор забезпечує це чотирма перевірками:

  1. Designated-ініціалізатор ініціалізує всі властивості свого класу до виклику super.init.
  2. Designated-ініціалізатор змінює успадковані властивості лише після super.init, інакше суперклас перезапише значення.
  3. Convenience-ініціалізатор викликає інший ініціалізатор до присвоєння будь-яких властивостей.
  4. До завершення фази 1 не можна викликати методи екземпляра, читати властивості чи звертатися до self як до значення.
Swift
class PinnedConnection: Connection {
    var pinnedKey: String

    init(host: String, pinnedKey: String) {
        self.pinnedKey = pinnedKey            // 1. свої властивості
        super.init(host: host, port: 443)     // 2. суперклас — кінець фази 1
        self.host = host.lowercased()         // 3. фаза 2: можна змінювати успадковане
        logSetup()                            //    і викликати методи
    }

    func logSetup() { print(host, port, pinnedKey) }
}
C#

У C# виклик : base(...) завжди перший. У Swift навпаки: спершу заповнюєш свої властивості, потім super.init(...). Так об'єкт ніколи не опиняється «напівготовим».

Успадкування й перевизначення ініціалізаторів

За замовчуванням підклас не успадковує ініціалізатори суперкласу. Інакше з'явилася б дірка: якби PinnedConnection успадкував init(host:port:), через нього можна було б створити з'єднання без pinnedKey.

Щоб перевизначити designated-ініціалізатор суперкласу, пишуть override — навіть якщо реалізуєш його як convenience. А от для convenience-ініціалізатора суперкласу override не пишуть: підклас не може викликати його напряму, тож це не перевизначення.

Swift
class LoggingConnection: Connection {
    override init(host: String, port: Int) {
        print("Підключаємось до \(host):\(port)")
        super.init(host: host, port: port)
    }
}

Дрібна зручність: якщо суперклас має синхронний init() без параметрів, а підклас після ініціалізації своїх властивостей більше нічого не робить, super.init() наприкінці можна не писати — компілятор підставить виклик сам.

Автоматичне успадкування ініціалізаторів

Ініціалізатори все ж успадковуються автоматично, якщо нові властивості підкласу мають значення за замовчуванням:

  • Правило 1. Якщо підклас не оголошує жодного designated-ініціалізатора, він успадковує всі designated-ініціалізатори суперкласу.
  • Правило 2. Якщо підклас має реалізації всіх designated-ініціалізаторів суперкласу (успадковані за правилом 1 або написані самостійно, зокрема як convenience), він успадковує й усі convenience-ініціалізатори.

Розглянемо мережевий клієнт:

Swift
import Foundation

class APIClient {
    let baseURL: URL
    let timeout: TimeInterval

    init(baseURL: URL, timeout: TimeInterval) {          // designated
        self.baseURL = baseURL
        self.timeout = timeout
    }

    convenience init(host: String) {                     // convenience
        self.init(baseURL: URL(string: "https://\(host)")!, timeout: 30)
    }
}

Правило 1 у дії. Мок для тестів лише додає властивість зі значенням за замовчуванням і не пише жодного ініціалізатора — тому отримує все:

Swift
final class RecordingClient: APIClient {
    var recordedPaths: [String] = []
}

let mock = RecordingClient(host: "example.com")   // і designated, і convenience

Правило 2 у дії. Клієнт з кешем додає властивість cache без значення за замовчуванням. Її треба заповнити, тому він пише власний designated-ініціалізатор з параметром cache. Правило 1 після цього не діє: власний designated є, отже init(baseURL:timeout:) батька не успадковується.

Чому від цього зникає й init(host:)? Подивись, що він робить усередині: викликає self.init(baseURL:timeout:). Для CachingClient такого ініціалізатора нема, а батьківський не знає про cache і залишив би поле порожнім. Тому компілятор не дає успадкувати init(host:): CachingClient(host:) дає помилку extra argument 'host' in call.

Щоб повернути init(host:), підклас сам реалізує init(baseURL:timeout:) і підставляє в ньому кеш за замовчуванням. Тепер усі designated-ініціалізатори батька є, і init(host:) успадковується:

Swift
final class CachingClient: APIClient {
    let cache: URLCache

    init(baseURL: URL, timeout: TimeInterval, cache: URLCache) {
        self.cache = cache
        super.init(baseURL: baseURL, timeout: timeout)
    }

    override convenience init(baseURL: URL, timeout: TimeInterval) {
        self.init(baseURL: baseURL, timeout: timeout, cache: .shared)
    }
}

let cached = CachingClient(host: "api.example.com")   // convenience успадковано

Ланцюжок виклику CachingClient(host: "api.example.com"):

  1. успадкований init(host:) викликає self.init(baseURL:timeout:);
  2. для CachingClient це перевизначена версія, яка викликає self.init(baseURL:timeout:cache:) з .shared;
  3. той заповнює cache і викликає super.init(baseURL:timeout:).

Кожне поле заповнене, тому компілятор і дозволяє успадкування.

Failable-ініціалізатори

Коли створення може не вдатися (неправильні параметри, відсутній ресурс), використовують init?. Він повертає опціонал, а невдачу позначають return nil:

Swift
struct Email {
    let value: String
    init?(_ raw: String) {
        guard raw.contains("@"), raw.count >= 3 else { return nil }
        value = raw
    }
}

if let email = Email("a@b.c") { print(email.value) }
Email("oops")   // nil

return nil тут — лише сигнал «створення не вдалося»; успішний шлях нічого не повертає, як і в звичайному init. Мати failable і звичайний ініціалізатор з однаковими параметрами не можна.

Порада

Числові перетворення в стандартній бібліотеці теж failable: Int(exactly: 3.5) повертає nil, а Int("42") — опціонал.

Failable-ініціалізатори для enum

Swift
enum Currency {
    case uah, usd, eur
    init?(code: String) {
        switch code.uppercased() {
        case "UAH": self = .uah
        case "USD": self = .usd
        case "EUR": self = .eur
        default: return nil
        }
    }
}

Для enum із сирими значеннями

Такі enum отримують init?(rawValue:) автоматично, і він повертає nil для невідомого значення:

Swift
enum Theme: String { case light, dark, system }

Theme(rawValue: "dark")      // .dark
Theme(rawValue: "sepia")     // nil — такого варіанта немає

Поширення невдачі

Failable-ініціалізатор може делегувати іншому failable — у value type вбік, у класі вбік або вгору. Якщо делегат повертає nil, увесь процес одразу завершується невдачею, і код після делегування не виконується:

Swift
struct HexColor {
    let rgb: UInt32

    init?(hex: String) {
        guard hex.count == 6, let value = UInt32(hex, radix: 16) else { return nil }
        rgb = value
    }

    init?(css: String) {                      // "#FF8800" або "ff8800"
        let trimmed = css.hasPrefix("#") ? String(css.dropFirst()) : css
        self.init(hex: trimmed)               // якщо nil — css-ініціалізатор теж nil
    }
}

HexColor(css: "#FF8800")?.rgb   // 16746496
HexColor(css: "#XYZ")           // nil

Failable може делегувати й звичайному ініціалізатору — це нормально.

Перевизначення failable-ініціалізатора

Підклас може замінити failable-ініціалізатор суперкласу звичайним, який ніколи не повертає nil (навпаки не можна):

Swift
class Slug {
    let text: String

    init(verified text: String) {                    // звичайний
        self.text = text
    }

    init?(_ raw: String) {                           // failable
        guard !raw.isEmpty, raw.allSatisfy({ $0.isLowercase || $0 == "-" }) else { return nil }
        text = raw
    }
}

final class LenientSlug: Slug {
    override init(_ raw: String) {                   // перевизначено як звичайний
        let cleaned = raw.lowercased()
            .map { $0.isLetter ? $0 : "-" }
        super.init(verified: String(cleaned))        // делегуємо не-failable ініціалізатору
    }
}

Slug("Hello World")          // nil
LenientSlug("Hello World")   // "hello-world" — ніколи не nil

init!

init! — варіант init?, який теж може повернути nil, але результат — неявно розгорнутий опціонал (Port!). Користуватися ним можна як звичайним значенням, без ? і if let. Якщо ж там nil, звернення спричинить крах.

Swift
struct Port {
    let value: Int

    init!(_ text: String) {
        guard let n = Int(text), (1...65535).contains(n) else { return nil }
        value = n
    }

    init(safe text: String) {   // звичайний init викликає init! усередині
        self.init(text)         // якщо там nil — крах
    }
}

let a: Port = Port("8080")      // результат одразу як Port
print(a.value)                  // 8080

print(Port("22").value)         // 22 — і без змінної теж

let b = Port("abc")             // без явного типу b стає звичайним Port?
print(b == nil)                 // true

let c = Port(safe: "443")
print(c.value)                  // 443

Зверни увагу на b: якщо тип не вказати, Swift робить зі змінної звичайний опціонал Port?, і b.value вже не скомпілюється без розгортання. «Неявне розгортання» спрацьовує, лише коли результат одразу використовують як Port.

Правила нижче стосуються делегування, тобто виклику одного ініціалізатора з іншого через self.init(...) чи super.init(...), як init(safe:) викликає init! у прикладі:

  • з init? можна викликати init! і навпаки;
  • зі звичайного init можна викликати init!, але якщо той поверне nil, буде крах, як при примусовому розгортанні. Тобто Port(safe: "abc") впаде;
  • у підкласі init? батька можна перевизначити як init! і навпаки.

На практиці init! трапляється рідко, здебільшого в старих API з Objective-C. У своєму коді майже завжди краще init?.

Required-ініціалізатори

required означає, що кожен підклас зобов'язаний реалізувати цей ініціалізатор. У підкласі теж пишуть required (а не override):

Swift
class Widget {
    required init() {}
}

class Slider: Widget {
    required init() {
        super.init()
    }
}

Коли підклас пише власний ініціалізатор, він втрачає автоматично успадковані — і required-ініціалізатори доводиться дописувати вручну. Саме тому в підкласі UIView з власним init з'являється обов'язковий required init?(coder:).

Значення за замовчуванням через замикання

Початкове значення властивості можна обчислити замиканням, яке одразу викликається (зверни увагу на () в кінці):

Swift
struct LootTable {
    let weights: [String: Int] = {
        var table: [String: Int] = [:]
        for rarity in ["common", "rare", "epic", "legendary"].enumerated() {
            table[rarity.element] = 1 << (6 - rarity.offset * 2)   // 64, 16, 4, 1
        }
        return table
    }()
}

Замикання виконується до ініціалізації решти екземпляра, тому в ньому не можна звертатися до інших властивостей, методів чи self. Без () властивості присвоювалося б саме замикання, а не результат.

Перевір себе

Обери відповідь — одразу побачиш, чи правильно, і пояснення.

1. Чому тут помилка компіляції?

Swift
struct Timer {
    var seconds: Double
    var label: String
    init() {
        seconds = 0
    }
}

До завершення ініціалізації кожна збережена властивість мусить мати значення. Автоматичних «нулів» немає.

2. Що надрукує цей код?

Swift
struct Counter {
    var value: Int {
        didSet { print("змінено на \(value)") }
    }
    init() { value = 1 }
    mutating func bump() { value += 1 }
}
var c = Counter()
c.bump()

Присвоєння в ініціалізаторі не викликає спостерігачів. Спрацьовує лише зміна в bump().

3. Що надрукує цей код?

Swift
struct Avatar {
    var name: String
    init(initials: String) { name = initials.uppercased() }
    init(_ raw: String) { name = raw }
}
print(Avatar(initials: "vs").name, Avatar("cat").name)

Ініціалізатори розрізняють за мітками. _ дозволяє викликати без мітки.

4. Яке твердження про let-властивість класу правильне?

Константу можна встановити один раз у будь-якому місці init. У класах це може зробити лише клас, що її оголосив.

5. Що надрукує цей код?

Swift
struct Tile {
    var x = 0
    var y = 0
}
let t = Tile(y: 5)
print(t.x, t.y)

Memberwise-ініціалізатор дозволяє пропустити параметри для властивостей зі значеннями за замовчуванням.

6. Чому тут помилка компіляції?

Swift
final class Session {
    var token: String
    var retries = 0
}
let s = Session()

init() без параметрів дається, лише якщо всі властивості мають значення за замовчуванням. Memberwise-ініціалізатора в класів немає.

7. Що надрукує цей код?

Swift
struct Policy {
    var attempts = 3
    var delay = 1.0
}
extension Policy {
    init(fast: Bool) {
        self.init(attempts: fast ? 10 : 1, delay: 0.1)
    }
}
let a = Policy()
let b = Policy(fast: true)
print(a.attempts, b.attempts)

Ініціалізатор у extension делегує memberwise-ініціалізатору, а автоматичні ініціалізатори зберігаються.

8. Що станеться, якщо init(fast:) з попереднього прикладу перенести з extension у саме оголошення структури?

Власний ініціалізатор в оголошенні прибирає обидва автоматичні. Тому допоміжні ініціалізатори тримають в extension.

9. Яке правило делегування в класах неправильне?

Designated делегують вгору, convenience — лише вбік, у межах свого класу.

10. Чому тут помилка компіляції?

Swift
class Connection {
    var host: String
    init(host: String) { self.host = host }
}
class Pinned: Connection {
    var key: String
    init(host: String, key: String) {
        super.init(host: host)
        self.key = key
    }
}

Фаза 1: спершу клас ініціалізує свої властивості, потім передає керування суперкласу.

11. Що надрукує цей код?

Swift
class Base {
    var name: String
    init(name: String) {
        self.name = name
        print("Base")
    }
}
class Child: Base {
    var level: Int
    init(level: Int) {
        self.level = level
        print("Child")
        super.init(name: "x")
        self.name = "child"
        print("Child: \(name)")
    }
}
_ = Child(level: 1)

Спершу підклас заповнює свої властивості, потім працює суперклас. Після super.init (фаза 2) можна змінювати успадковане.

12. Чому тут помилка компіляції?

Swift
class Client {
    let host: String
    init(host: String) { self.host = host }
}
final class CachingClient: Client {
    let size: Int
    init(host: String, size: Int) {
        self.size = size
        super.init(host: host)
    }
}
let c = CachingClient(host: "a.com")

За замовчуванням ініціалізатори не успадковуються. Інакше можна було б створити об'єкт без size.

13. Що надрукує цей код?

Swift
class Client {
    let host: String
    let timeout: Int
    init(host: String, timeout: Int) {
        self.host = host
        self.timeout = timeout
    }
    convenience init(host: String) {
        self.init(host: host, timeout: 30)
    }
}
final class MockClient: Client {
    var calls: [String] = []
}
let m = MockClient(host: "test")
print(m.host, m.timeout, m.calls.count)

Підклас без власних designated-ініціалізаторів успадковує всі designated, а отже й convenience-ініціалізатори.

14. Коли перед ініціалізатором підкласу пишуть override?

Convenience-ініціалізатор суперкласу підклас не може викликати напряму, тож його «заміна» — не перевизначення.

15. Що надрукує цей код?

Swift
struct Email {
    let value: String
    init?(_ raw: String) {
        guard raw.contains("@") else { return nil }
        value = raw
    }
}
print(Email("oops")?.value ?? "немає", Email("a@b")?.value ?? "немає")

init? повертає опціонал: nil, якщо спрацював return nil.

16. Що надрукує цей код?

Swift
enum Theme: String { case light, dark }
print(Theme(rawValue: "sepia") == nil, Theme(rawValue: "dark") == .dark)

Enum із сирими значеннями отримує init?(rawValue:), що дає nil для невідомого значення.

17. Що надрукує цей код?

Swift
struct Hex {
    let value: Int
    init?(hex: String) {
        guard let v = Int(hex, radix: 16) else { return nil }
        value = v
    }
    init?(css: String) {
        self.init(hex: String(css.dropFirst()))
        print("готово")
    }
}
print(Hex(css: "#zz") == nil)

Якщо делегат повернув nil, увесь ініціалізатор одразу завершується невдачею, і код після делегування не виконується.

18. Яке твердження неправильне?

init? і init! взаємозамінні при перевизначенні й делегуванні.

19. Чому тут помилка компіляції?

Swift
class Widget {
    let id: Int
    required init(id: Int) { self.id = id }
}
class Slider: Widget {
    let value: Double
    init(value: Double) {
        self.value = value
        super.init(id: 0)
    }
}

Коли підклас пише свій ініціалізатор, він втрачає успадковані, а required мусить бути в кожному підкласі.

20. Яке слово пишуть у підкласі перед реалізацією required-ініціалізатора суперкласу?

У підкласі знову пишуть required — так вимога передається далі по ієрархії. override не потрібен.

21. Що надрукує цей код?

Swift
struct Table {
    let squares: [Int] = {
        var result: [Int] = []
        for i in 1...3 { result.append(i * i) }
        return result
    }()
}
print(Table().squares)

Замикання з () наприкінці одразу викликається, і властивість отримує його результат.

22. Чому в такому замиканні не можна звертатися до інших властивостей чи self?

Коли рахується значення за замовчуванням, екземпляр ще не готовий.

Практика
  1. Зроби struct Color з ініціалізаторами init(red:green:blue:), init(white:) і failable init?(hex: String). Збережи memberwise-ініціалізатор.
  2. Побудуй ієрархію Account → PremiumAccount з designated і convenience ініціалізаторами. Додай у PremiumAccount властивість зі значенням за замовчуванням і перевір, які ініціалізатори успадкувались.
  3. Свідомо порушуй кожну з чотирьох перевірок двофазної ініціалізації й прочитай помилки компілятора.
  4. Зроби enum Plan: String і failable-ініціалізатор init?(productID:), що розбирає ідентифікатори App Store на кшталт com.app.pro.monthly.
