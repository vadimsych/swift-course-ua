Безпека пам'яті

Що таке конфліктний доступ до пам'яті, чому Swift забороняє певні комбінації inout, mutating і властивостей, і як ці правила пов'язані з ексклюзивністю доступу.

У книзі: memorysafety

Конфліктний доступ до пам'яті

Доступ до пам'яті відбувається постійно: читання змінної, присвоєння, передача в inout. Swift гарантує, що запис у певну ділянку пам'яті не перетинається з іншим доступом до неї. Це правило називають ексклюзивністю доступу.

Навіть в однопотоковому коді можна випадково отримати ситуацію, коли одна операція змінює значення, поки інша його читає. Наприклад: функція отримала inout-посилання на змінну, а всередині читає ту саму змінну напряму. Результат залежав би від деталей реалізації, тому Swift вважає це помилкою.

Коли два доступи конфліктують

Найпростіше думати так: конфлікт — це коли хтось пише в пам'ять, поки хтось інший її використовує, і ці два моменти накладаються в часі. Точніше, конфлікт є, якщо:

  • обидва доступи стосуються тієї самої змінної, властивості чи елемента;
  • це не два читання (хоча б один пише);
  • це не два атомарні доступи (типи на кшталт Atomic з модуля Synchronization чи атомарні операції C спеціально призначені для одночасної роботи);
  • тривалості доступів перекриваються.

Більшість доступів миттєві: прочитати змінну чи присвоїти їй значення — це одна дія, під час якої ніщо інше не встигає відбутися. Але деякі доступи тривалі:

  • inout-параметр утримує доступ на запис від моменту, коли обчислено всі звичайні аргументи, до повернення з функції (кілька inout-параметрів отримують доступ по черзі, зліва направо);
  • mutating-метод утримує доступ на запис до всього self на час виклику;
  • оператор з inout-операндом (як += чи власний) — так само, як функція.

Конфлікт можливий лише тоді, коли хоча б один з доступів тривалий.

Конфлікти з inout-параметрами

inout-параметр має тривалий доступ на запис на весь час виклику. Тому, поки функція працює, ніхто інший не може звертатися до тієї самої змінної — навіть опосередковано, наприклад через замикання:

Swift
var balance = 100
let showBalance = { print("Баланс:", balance) }     // замикання читає balance

func charge(_ amount: Int, from value: inout Int, notify: () -> Void) {
    value -= amount
    notify()        // читання balance, поки триває запис через inout
}

var bonus = 50
charge(10, from: &bonus, notify: showBalance)     // ок: різні змінні
charge(10, from: &balance, notify: showBalance)   // конфлікт — крах у рантаймі

Розв'язок — розвести доступи в часі, наприклад через локальну копію:

Swift
var working = balance
charge(10, from: &working, notify: showBalance)
balance = working

Передача однієї змінної у два inout — завжди конфлікт, і його компілятор ловить одразу:

Swift
func transfer(_ amount: Int, from: inout Int, to: inout Int) {
    from -= amount
    to += amount
}

var wallet = 100, bank = 500
transfer(10, from: &wallet, to: &bank)       // ок
// transfer(10, from: &wallet, to: &wallet)  // помилка компіляції
C#

У C# одну змінну можна передати в два ref-параметри. У Swift — ні: компілятор вважає це помилкою, бо незрозуміло, яке значення має лишитись у змінній.

Конфлікти з self у методах

mutating-метод має тривалий доступ на запис до всього self на час виклику. Тому передати в нього як inout частину того самого значення не можна:

Swift
struct Shop {
    var gold = 0
    var stock = ["sword", "shield"]

    mutating func sell(_ item: String, earnings: inout Int) {
        stock.removeAll { $0 == item }
        earnings += 25
    }
}

var shop = Shop()
var pocket = 0
shop.sell("sword", earnings: &pocket)        // ок: pocket — окрема змінна
// shop.sell("shield", earnings: &shop.gold) // помилка: self і shop.gold перекриваються

Правильно — або змінювати gold усередині методу, або передати окрему змінну й потім записати результат.

Конфлікти з властивостями

Для value types (структури, кортежі, enum) усе значення — одна ділянка пам'яті: змінити властивість означає змінити все значення. Для класів кожна збережена властивість — окрема ділянка, бо екземпляр живе в купі, а змінна лише посилається на нього.

Візьмемо прямокутник кнопки, який треба «перетягнути» між двома своїми полями — функцією з двома inout:

Swift
struct Frame { var width = 100.0; var height = 40.0 }
final class FrameBox { var width = 100.0; var height = 40.0 }

func shift(_ delta: Double, from a: inout Double, to b: inout Double) {
    a -= delta
    b += delta
}

func layout() {
    var frame = Frame()
    shift(10, from: &frame.width, to: &frame.height)      // ок: компілятор бачить усю функцію

    let box = FrameBox()
    shift(10, from: &box.width, to: &box.height)          // ок: поля об'єкта — окремі ділянки
}

func layoutLater() -> () -> Void {
    var frame = Frame()
    let render = { print(frame.width) }                   // escaping-замикання захопило frame
    // shift(10, from: &frame.width, to: &frame.height)   // крах у рантаймі: frame тепер видно ззовні функції
    return render
}

Компілятор дозволяє одночасний доступ до різних збережених властивостей структури лише тоді, коли може довести, що ніхто інший не бачить цю змінну. Для локальної змінної, яку не захопило escaping-замикання, це легко довести. Якщо ж змінна глобальна, є властивістю класу чи її захопило escaping-замикання, компілятор не знає, хто ще до неї звернеться, і вважає доступ до будь-якого поля доступом до всього значення. Залежно від ситуації це помилка компіляції або (як із захопленою змінною вище) перевірка в рантаймі з крахом.

Послаблення не діє для обчислюваних властивостей і властивостей типу (static/class): доступ через геттер чи сеттер завжди зачіпає все значення.

Ці правила суворіші, ніж потрібно для фізичної безпеки пам'яті — частина коду, яку компілятор відкидає, насправді коректна. Але така суворість дає змогу перевіряти все локально й дешево.

Порада

Конфлікти ексклюзивності на практиці трапляються рідко, а повідомлення компілятора зазвичай чітко вказує, де саме перетнулися доступи. Майже завжди розв'язок — тимчасова локальна копія значення.

Перевір себе

Обери відповідь — одразу побачиш, чи правильно, і пояснення.

1. Що гарантує правило ексклюзивності доступу?

Swift не дозволяє, щоб запис накладався в часі з іншим доступом до тієї самої пам'яті.

2. Чи можливий конфлікт доступу в однопотоковому коді?

Тривалий доступ на запис через inout може перекритися з читанням тієї самої змінної навіть в одному потоці.

3. Яке твердження неправильне?

Конфлікт можливий лише тоді, коли хоча б один з доступів тривалий, а їхні тривалості перекриваються.

4. Що станеться при запуску цього коду?

Swift
func charge(_ amount: Int, from value: inout Int, notify: () -> Void) {
    value -= amount
    notify()
}

func run() {
    var balance = 100
    let show = { print("Баланс:", balance) }
    charge(10, from: &balance, notify: show)
}
run()

Поки charge утримує доступ на запис до balance, замикання читає ту саму змінну. Swift ловить це перевіркою в рантаймі.

5. Що станеться з цим кодом?

Swift
func transfer(_ amount: Int, from: inout Int, to: inout Int) {
    from -= amount
    to += amount
}

func run() {
    var wallet = 100
    transfer(10, from: &wallet, to: &wallet)
    print(wallet)
}
run()

Передача однієї змінної у два inout-параметри — завжди конфлікт, і компілятор ловить його одразу.

6. Чому тут помилка компіляції?

Swift
struct Shop {
    var gold = 0
    var stock = ["sword", "shield"]

    mutating func sell(_ item: String, earnings: inout Int) {
        stock.removeAll { $0 == item }
        earnings += 25
    }
}

func run() {
    var shop = Shop()
    shop.sell("sword", earnings: &shop.gold)
}
run()

Доступ до self і доступ до shop.gold перекриваються. Розв'язок — окрема змінна або зміна gold усередині методу.

7. Що надрукує цей код?

Swift
struct Frame { var width = 100; var height = 40 }

func shift(_ d: Int, from a: inout Int, to b: inout Int) {
    a -= d
    b += d
}

func run() {
    var frame = Frame()
    shift(10, from: &frame.width, to: &frame.height)
    print(frame.width, frame.height)
}
run()

Для локальної структури, яку не захопило escaping-замикання, компілятор доводить, що доступи до різних збережених властивостей не перетинаються.

8. Яке твердження неправильне?

Доступ через геттер чи сеттер обчислюваної властивості завжди зачіпає все значення.

Практика
  1. Напиши функцію з inout-параметром, яка всередині читає глобальну змінну, і виклич її, передавши ту саму змінну. Подивись на повідомлення в рантаймі.
  2. Відтвори конфлікт mutating-методу, в який передано власну властивість як inout, і виправ його.
  3. Напиши власний оператор <->, що міняє місцями два inout-операнди, і перевір, що буде при a <-> a.
  4. Перевір різницю між перекриттям доступів до властивостей локальної структури, структури, захопленої escaping-замиканням, і об'єкта класу.
