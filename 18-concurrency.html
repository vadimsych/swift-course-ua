Мова крок за кроком · урок 18

Конкурентність

async/await, асинхронні послідовності, async let, задачі й групи задач, скасування, неструктуровані задачі, ізоляція, @MainActor, актори, глобальні актори й Sendable. Урок довгий, бо в Swift 6 конкурентність перевіряє компілятор, і без цих понять код просто не збереться.

У книзі: concurrency

Асинхронні функції

Функція, що може призупинитися посередині виконання, позначається async. Виклик позначається await — це точка призупинення, де потік може бути відданий іншій роботі.

Swift
func fetchBalance(userID: Int) async -> Int {
    try? await Task.sleep(for: .milliseconds(300))   // імітація мережі
    return 1_250
}

func refreshHeader() async {
    let balance = await fetchBalance(userID: 7)
    print("Баланс: \(balance)")
}

Якщо функція і асинхронна, і може кинути помилку, порядок — async throws, а при виклику — try await:

Swift
func loadProfile() async throws -> String { "Vadim" }
let name = try await loadProfile()

Викликати асинхронну функцію можна лише з асинхронного контексту: з іншої async-функції, з Task { }, з методу .task { } у SwiftUI, з static func main() async в @main-типі.

Порада

Плануючи міграцію старого коду на async/await, починай з точок входу — обробників кнопок, onAppear, делегатів застосунку — і рухайся до мережевого шару. Навпаки не вийде: синхронна функція не вміє «почекати» на асинхронну, вона може лише запустити Task і жити далі.

Між точками await код виконується без переривань з боку інших задач того самого актора. Але після await світ міг змінитися: інші задачі могли змінити стан. Це головне, що треба тримати в голові.

C#

Синтаксис майже такий самий, як у C# і UniTask. Відмінності: результат не загортається в Task<T> — функція просто повертає T; на якому потоці продовжиться код, вирішує актор (про це нижче), а не ConfigureAwait; немає async void — «запустити й забути» пишуть явно через Task { }.

Асинхронні послідовності

for await перебирає послідовність, елементи якої надходять з часом:

Swift
import Foundation

let url = URL(fileURLWithPath: "/tmp/log.txt")
for try await line in url.lines {
    print(line)
}

Власні послідовності роблять, реалізуючи протокол AsyncSequence або, найпростіше, через AsyncStream:

Swift
func ticks(count: Int) -> AsyncStream<Int> {
    AsyncStream { continuation in
        Task {
            for i in 1...count {
                try? await Task.sleep(for: .seconds(1))
                continuation.yield(i)
            }
            continuation.finish()
        }
    }
}

for await t in ticks(count: 3) { print("тік", t) }
C#

Аналог — IAsyncEnumerable<T> і await foreach. У StoreKit 2 ти вже зустрічав такий потік: Transaction.updates.

Паралельний виклик: async let

await одразу чекає результат. Щоб запустити кілька операцій паралельно, використовують async let:

Swift
func loadHome() async throws {
    async let profile = loadProfile()
    async let balance = fetchBalance(userID: 7)
    async let offers = loadOffers()

    let screen = try await (profile, balance, offers)   // чекаємо всі три
    render(screen)
}

async let запускає дочірню задачу одразу. Чекання відбувається там, де значення використовується. Якщо функція завершиться, не дочекавшись (наприклад, через помилку), незавершені дочірні задачі буде скасовано й дочекано автоматично.

C#

Як запустити кілька Task і зробити await Task.WhenAll(...), але структуровано: задачі не можуть «загубитися» і пережити функцію.

Задачі й групи задач

Задача (Task) — одиниця асинхронної роботи. Усі асинхронні функції виконуються в якійсь задачі. async let створює дочірню задачу неявно.

Коли кількість паралельних операцій відома лише в рантаймі, використовують групу задач:

Swift
func downloadAll(_ ids: [Int]) async -> [Int: Data] {
    await withTaskGroup(of: (Int, Data?).self) { group in
        for id in ids {
            group.addTask {
                (id, try? await download(id: id))
            }
        }

        var result: [Int: Data] = [:]
        for await (id, data) in group {      // результати в порядку завершення
            if let data { result[id] = data }
        }
        return result
    }
}

Варіанти групи:

  • withThrowingTaskGroup — дочірні задачі можуть кидати помилки. Помилка не скасовує решту задач сама: її отримаєш, коли читатимеш результати. Щоб зупинити все одразу, виклич group.cancelAll().
  • withDiscardingTaskGroup / withThrowingDiscardingTaskGroup — коли результати не потрібні; у throwing-варіанті перша помилка скасовує всю групу.
  • group.addTaskUnlessCancelled { } — додає задачу лише якщо група ще не скасована і повертає Bool, чи задачу додано.

Задачі утворюють дерево: батьківська задача не завершиться, поки не завершаться всі дочірні. Це і називається структурованою конкурентністю. Що вона дає:

  • дочірня задача не переживе батьківську;
  • скасування батьківської автоматично поширюється на дочірні;
  • помилки й результати повертаються туди, звідки задачу запустили;
  • якщо дочірня задача отримує вищий пріоритет, ніж батьківська, пріоритет батьківської підвищується;
  • task-local значення (@TaskLocal, наприклад ID запиту для логування) автоматично доступні в дочірніх задачах.

Скасування

Скасування в Swift кооперативне: воно лише ставить прапорець, а задача сама вирішує, як реагувати.

Swift
func processFrames(_ frames: [Frame]) async throws -> [Frame] {
    var output: [Frame] = []
    for frame in frames {
        try Task.checkCancellation()          // кидає CancellationError, якщо скасовано
        output.append(await enhance(frame))
    }
    return output
}

// або без помилки:
if Task.isCancelled {
    return partialResult
}

Більшість системних асинхронних API самі перевіряють скасування: Task.sleep кидає CancellationError, а URLSession — URLError(.cancelled). Ззовні задачі перевірити її стан можна через властивість екземпляра: loadTask.isCancelled.

Щоб відреагувати на скасування негайно (наприклад, закрити сокет), є обробник:

Swift
let data = try await withTaskCancellationHandler {
    try await socket.receive()
} onCancel: {
    socket.close()        // викликається одразу при скасуванні, з будь-якого потоку
}

Обробник скасування може виконуватися одночасно з основним тілом, тому не діли між ними змінюваний стан без синхронізації.

C#

Замість CancellationToken, який доводиться прокидати в кожну функцію, тут скасування «живе» в самій задачі: перевіряй Task.isCancelled будь-де. У SwiftUI .task { } сам скасовує задачу, коли екран зникає — як GetCancellationTokenOnDestroy() в UniTask.

Неструктуровані задачі

Іноді задачу треба запустити з синхронного коду або щоб вона жила незалежно — для цього Task { }:

Swift
@MainActor
final class PaywallViewModel {
    private var loadTask: Task<Void, Never>?

    func onAppear() {
        loadTask = Task {
            await loadProducts()
        }
    }

    func onDisappear() {
        loadTask?.cancel()       // неструктуровану задачу скасовуєш сам
    }
}

let handle = Task { await fetchBalance(userID: 1) }
let value = await handle.value   // дочекатися результату
  • Task { } успадковує від місця створення ізоляцію (актор), пріоритет і task-local значення.
  • Task.detached { } нічого не успадковує. Потрібен рідко.
  • За життя й скасування неструктурованої задачі відповідаєш сам: тримай Task і скасовуй його.
Пастка

Task { } у методі класу сильно захоплює self до завершення задачі. Для довгих задач (нескінченний for await) використовуй [weak self] і перевіряй self на кожній ітерації, або скасовуй задачу явно.

Ізоляція

Data race — це коли два потоки одночасно звертаються до однієї змінюваної пам'яті, і хоча б один пише. Swift 6 запобігає цьому статично: компілятор доводить, що кожен шматок змінюваного стану в будь-який момент доступний лише з одного місця.

Коли компілятор свариться на data race, постав собі три запитання. Значення змінюється? Якщо ні (let) — проблеми немає. Його бачить хтось, крім цієї задачі? Якщо ні (локальна змінна) — теж нормально. Якщо і змінюється, і спільне — його має охороняти актор.

Код, що не належить жодному актору, — неізольований (nonisolated): він може працювати будь-де, але до ізольованого стану звертається лише через await. Перехід між областями ізоляції — завжди точка await.

Головний актор

@MainActor — глобальний актор для UI. Увесь код UIKit і SwiftUI ізольований на ньому. На практиці код головного актора виконується на головному потоці, але думати варто в термінах актора: компілятор перевіряє саме ізоляцію.

Swift
@MainActor
final class ScoreViewModel {
    var score = 0                      // доступно лише з головного актора

    func add(_ points: Int) {
        score += points
    }
}

@MainActor
func updateLabel(_ text: String) { /* ... */ }

func backgroundWork() async {
    let result = await heavyComputation()
    await updateLabel("Готово: \(result)")   // перехід на головний актор
}
  • Атрибут на типі ізолює всі його члени. Окремий член можна вивести з ізоляції через nonisolated — або навпаки, позначити @MainActor лише одну властивість чи метод неізольованого типу.
  • Ізоляція успадковується: підклас @MainActor-класу і тип, що відповідає @MainActor-протоколу, теж на головному акторі. Саме тому будь-який SwiftUI View неявно @MainActor — так оголошено протокол View.
  • Властивість з property wrapper, у якого wrappedValue ізольований на @MainActor, теж стає @MainActor.
  • Замикання задачі можна ізолювати явно: Task { @MainActor in label.text = "Готово" }.
  • Для одноразового виконання на головному акторі є await MainActor.run { ... }.
  • Замикання можна позначити як @MainActor () -> Void.
Swift 6

У нових проєктах Xcode зазвичай увімкнено режим, де весь код за замовчуванням працює на головному акторі (налаштування Default Actor Isolation). Тоді фонову роботу явно виносять атрибутом @concurrent. Перевір, як налаштований твій таргет.

Swift 6

Ще одне налаштування, Approachable Concurrency, робить так, що звичайна async-функція продовжує роботу там, звідки її викликали, а не перескакує у фоновий потік. Це спрощує код, але вмикається окремо.

C#

@MainActor — це формалізований UnityMainThreadDispatcher чи await UniTask.SwitchToMainThread(), тільки компілятор не дасть торкнутися UI з фонового потоку взагалі.

Актори

Актор — reference type, як клас, але його змінюваний стан доступний лише з однієї задачі одночасно. Звернення ззовні проходить через await, бо, можливо, доведеться почекати, поки актор звільниться.

Swift
actor TokenStore {
    private var token: String?
    private var refreshCount = 0

    func current() -> String? { token }

    func update(_ new: String) {
        token = new
        refreshCount += 1
    }
}

let store = TokenStore()
await store.update("abc")
let t = await store.current()
  • Усередині актора await для власних членів не потрібен: код уже ізольований.
  • Актори не підтримують успадкування.
  • nonisolated члени можна викликати без await, але вони не мають доступу до змінюваного стану.

Реентерабельність

Поки актор чекає на await, інші задачі можуть виконувати його методи. Тому стан між двома await може змінитися:

Swift
actor ImageCache {
    private var cache: [URL: Image] = [:]

    func image(for url: URL) async throws -> Image {
        if let cached = cache[url] { return cached }
        let image = try await download(url)   // тут інший виклик міг уже завантажити те саме
        cache[url] = image
        return image
    }
}

Правило: після кожного await перевіряй стан заново — поки функція «спала», інший виклик міг його змінити. А зміни, які на мить роблять стан некоректним, пиши в синхронних методах актора: там немає await, тож ніхто не втрутиться посередині.

C#

Уяви клас, де весь код автоматично обгорнутий у lock, — тільки без блокування потоків і без дедлоків. Різниця з lock одна: на кожному await актор «відпускає замок», тож інший виклик може встигнути щось змінити.

Глобальні актори

Глобальний актор — актор-синглтон, атрибутом якого можна позначити будь-які типи, функції чи змінні. @MainActor — один з них. Можна оголосити власний:

Swift
@globalActor
actor DatabaseActor {
    static let shared = DatabaseActor()
}

@DatabaseActor
final class LocalStorage {
    var records: [String] = []
    func add(_ r: String) { records.append(r) }
}

Усе, що позначено @DatabaseActor, виконується послідовно в одній області ізоляції, навіть якщо розкидано по різних типах.

Sendable

Між областями ізоляції можна передавати лише значення, які безпечно ділити. Такі типи відповідають протоколу Sendable:

  • value types (struct, enum), усі збережені властивості яких Sendable;
  • актори;
  • final класи лише з незмінними let-властивостями Sendable-типів;
  • класи, ізольовані на глобальному акторі (наприклад, @MainActor-класи);
  • final класи, змінюваний стан яких лежить у let-властивостях Sendable-типів на кшталт Mutex — компілятор перевіряє їх без жодних позначок;
  • класи з ручною синхронізацією, яку компілятор не бачить (NSLock, черга DispatchQueue), — з позначкою @unchecked Sendable;
  • функції та замикання, позначені @Sendable (захоплюють лише Sendable-значення).
Swift
struct Score: Sendable {        // для внутрішніх структур і так виводиться автоматично
    let points: Int
    let player: String
}

final class Config: Sendable {
    let apiURL: URL
    init(apiURL: URL) { self.apiURL = apiURL }
}

final class Counter {           // не Sendable: змінюваний стан
    var value = 0
}

Для непублічних структур і enum компілятор виводить Sendable сам, якщо всі поля Sendable. Для публічних типів відповідність пишуть явно, бо це частина контракту API.

Значення, що не є Sendable, теж можна передати в іншу область ізоляції, якщо компілятор доведе, що після передачі в старій області на нього ніхто не посилається. Для параметрів і результатів це позначається словом sending.

Щоб явно заборонити типу бути Sendable (навіть якщо компілятор вивів би це автоматично), пишуть недоступне розширення: @available(*, unavailable) extension Cursor: Sendable {}.

Пастка

@unchecked Sendable вимикає перевірку компілятора. Це твоє «повір мені», і data race буде на твоїй совісті. Використовуй лише тоді, коли синхронізація справді є всередині.

Порада

При міграції старого коду, що використовує бібліотеки без анотацій конкурентності, допомагає @preconcurrency import SomeSDK: попередження про Sendable з цього модуля приглушуються, поки бібліотека не оновиться.

Перевір себе

Обери відповідь — одразу побачиш, чи правильно, і пояснення.

1. Що означає await перед викликом?

await — точка призупинення. Після неї стан міг змінитися, бо інший код встиг попрацювати.

2. Як запустити два завантаження паралельно й дочекатися обох?

async let одразу запускає дочірню задачу, а чекання відбувається там, де значення використовується. Аналог Task.WhenAll у C#.

3. Яке твердження про скасування задачі неправильне?

Скасування лише ставить прапорець. Задача продовжує виконуватися, доки сама не перевірить його або не дійде до API, що реагує на скасування.

4. Що гарантує актор?

Тому звертання ззовні до актора йде через await: можливо, доведеться почекати, поки актор звільниться.

5. Для чого @MainActor?

Увесь UI-код ізольований на головному акторі. Компілятор не дасть торкнутися UI з фонового контексту без переходу через await.

6. Які типи безпечно передавати між потоками (Sendable)?

Небезпечний лише змінюваний стан, яким діляться без захисту. Тому звичайний клас з var-властивостями не Sendable.

Практика
  1. Напиши async-функцію, що паралельно через async let завантажує профіль, баланс і список продуктів, і виміряй час порівняно з послідовними await.
  2. Через withThrowingTaskGroup завантаж 10 URL з обмеженням: не більше 3 одночасно.
  3. Зроби actor RateLimiter з методом func allow() -> Bool, що дозволяє не більше N викликів за секунду.
  4. Зроби @MainActor final class ViewModel з методом, що запускає Task, завантажує дані у фоновій @concurrent-функції і оновлює властивість. Додай скасування при закритті екрана.
  5. Створи клас зі змінюваним станом, передай його екземпляр у Task.detached і після цього використай той самий екземпляр у поточній функції. Прочитай помилку компілятора й виправ її трьома різними способами. (Без використання після передачі компілятор помилки не покаже — він доводить, що екземпляр більше ніхто не чіпає.)
