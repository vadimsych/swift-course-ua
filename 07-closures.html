Замикання

Лямбди Swift для C#-розробника: як вони записуються (від повної форми до найкоротшої), trailing closures, захоплення змінних, чому замикання — reference type, @escaping і @autoclosure.

У книзі: closures

Що ти вже знаєш з C

Лямбда x => x * 2, делегати Func<>/Action<>, захоплення змінних у display class — усе це в Swift є і називається замиканнями. Причому в Swift немає різниці між «методом» і «лямбдою» як значеннями: іменована функція, вкладена функція й вираз у фігурних дужках однаково можна покласти в змінну чи передати аргументом. Відрізняються вони лише тим, чи мають ім'я і чи захоплюють щось з оточення.

Синтаксис: усі форми в одній таблиці

Візьмемо функцію вищого порядку, яку напишемо самі — повторювач спроб:

Swift
func retry(_ times: Int, _ attempt: (Int) -> Bool) -> Bool {
    for n in 1...times where attempt(n) { return true }
    return false
}

Той самий виклик з різним ступенем скорочення:

Форма Запис
повна retry(3, { (n: Int) -> Bool in return connect(n) })
типи виведено з контексту retry(3, { n in return connect(n) })
неявний return (один вираз) retry(3, { n in connect(n) })
скорочені імена аргументів retry(3, { connect($0) })
trailing closure retry(3) { connect($0) }
готова функція замість замикання retry(3, connect)

Що варто знати:

  • Заголовок замикання відокремлюється від тіла словом in. Параметри замикань можуть бути inout чи variadic, але не мати значень за замовчуванням.
  • Типи можна не писати, коли їх знає функція, якій передаєш замикання. Без контексту вираз { n in n * 2 } не скомпілюється — компілятор не знає тип n.
  • $0, $1… доступні, коли список параметрів не написано; кількість параметрів виводиться з контексту.
  • Оператор — теж функція: scores.sorted(by: >) передає > як (Int, Int) -> Bool.
C#

Як у C# від delegate (int n) { ... } дійшли до n => Connect(n), так і тут: повну форму пишуть рідко, а найчастіше — { $0 ... } або просто ім'я функції.

Trailing closures

Якщо останні аргументи — замикання, їх пишуть після дужок. Якщо замикання єдиний аргумент, дужки зникають зовсім. Кілька замикань наприкінці пишуться одне за одним, і всі, крім першого, — з мітками:

Swift
func fade(duration: Double,
          step: (Double) -> Void,
          completion: () -> Void) { }

fade(duration: 0.3) { alpha in
    print("Прозорість", alpha)
} completion: {
    print("Анімацію завершено")
}

На trailing closures побудований синтаксис SwiftUI: VStack { ... }, Button("OK") { ... }, .task { ... }.

Захоплення змінних

Замикання бачить змінні з місця створення і тримає їх стільки, скільки живе саме. Практичний приклад — обмежувач частоти подій, щоб аналітика не отримувала той самий тап частіше, ніж раз на пів секунди:

Swift
import Foundation

func throttled(interval: TimeInterval, _ action: @escaping () -> Void) -> () -> Void {
    var lastRun = Date.distantPast          // захоплена змінна живе разом із замиканням
    return {
        let now = Date()
        guard now.timeIntervalSince(lastRun) >= interval else { return }
        lastRun = now                       // замикання змінює захоплену змінну
        action()
    }
}

let trackTap = throttled(interval: 0.5) { print("tap sent") }
trackTap()   // tap sent
trackTap()   // нічого: з минулого виклику минуло менше 0.5 с

Функція throttled давно завершилась, а lastRun живе в замиканні й оновлюється між викликами.

Захоплюється змінна, а не її значення в момент створення:

Swift
var multiplier = 2
let scale = { (x: Int) in x * multiplier }
multiplier = 10
scale(3)     // 30, а не 6

Щоб «заморозити» значення, його вказують у capture list: { [multiplier] (x: Int) in x * multiplier } — тоді результат буде 6.

C#

Працює так само, як захоплення змінних у лямбдах C#. Плюс одна пастка менше: змінна циклу for-in на кожній ітерації нова, тож лямбди в циклі не «бачать» одне й те саме значення.

Замикання — reference type

Якщо одне замикання покласти в кілька місць, усі вони вказують на той самий об'єкт із тим самим захопленим станом:

Swift
let trackSwipe = throttled(interval: 0.5) { print("swipe sent") }

var handlers: [String: () -> Void] = [:]
handlers["left"] = trackSwipe
handlers["right"] = trackSwipe      // те саме замикання, спільний lastRun

handlers["left"]?()                 // swipe sent
handlers["right"]?()                // нічого: вікно 0.5 с спільне

Звідси й головний ризик — цикли сильних посилань, коли об'єкт тримає замикання, а замикання тримає об'єкт. Детально в уроці про ARC.

Escaping-замикання

Замикання втікає (escapes), якщо переживає виклик функції, якій його передали: його зберегли у властивості, поставили в чергу, викликали асинхронно. Такий параметр позначають @escaping; без позначки компілятор не дасть його зберегти:

Swift
final class EventBus {
    private var subscribers: [(String) -> Void] = []

    func subscribe(_ handler: @escaping (String) -> Void) {
        subscribers.append(handler)
    }

    func forEachSubscriber(_ body: ((String) -> Void) -> Void) {
        subscribers.forEach(body)     // body викликається одразу — @escaping не потрібен
    }
}

За замовчуванням параметри-замикання non-escaping: компілятор знає, що вони не переживуть виклик, і може оптимізувати їх.

Чому компілятор змушує писати self

Ось баг, який Swift намагається попередити:

Swift
final class CartBadge {
    var itemCount = 0
    let bus = EventBus()

    func connect() {
        bus.subscribe { _ in self.itemCount += 1 }   // CartBadge → bus → замикання → CartBadge
    }
}

CartBadge тримає bus, bus тримає замикання, замикання тримає CartBadge. Вийшло коло, і жоден з об'єктів не звільниться. Тому в escaping-замиканні класу Swift вимагає згадати self явно — щоб це рішення було свідомим. Правильніше так:

Swift
bus.subscribe { [weak self] _ in self?.itemCount += 1 }

У non-escaping замиканнях (як forEach) і в коді структур чи enum self. писати не обов'язково: циклу там не буде. Але змінити self структури з escaping-замикання не можна — коли воно виконається, mutating-метод уже завершиться.

C#

C# не розрізняє escaping і non-escaping — будь-яку лямбду можна зберегти. У Swift компілятор знає, які замикання живуть довше за виклик, і саме для них змушує подумати про пам'ять.

Autoclosures

@autoclosure загортає аргумент-вираз у замикання автоматично. Виклик виглядає як передача звичайного значення, а обчислюється вираз лише тоді, коли функція до нього звернеться:

Swift
func debugLog(_ message: @autoclosure () -> String) {
    #if DEBUG
    print(message())
    #endif
}

debugLog("Стан кошика: \(cart.dump())")   // у релізній збірці dump() не викликається

Так влаштовані ??, &&, || і assert. Якщо таке замикання треба зберегти, пишуть @autoclosure @escaping. Головний ризик autoclosure — з місця виклику не видно, що вираз може й не обчислитися, тож у власних API застосовуй її рідко.

Практика
  1. Відсортуй масив гравців (name: String, score: Int) за спаданням очок, а при рівності — за іменем. Спробуй кожну форму з таблиці.
  2. Напиши func debounce(_ action: @escaping () -> Void) -> () -> Void, що запускає action лише на кожен третій виклик.
  3. Поясни, чому sorted(by:) не потребує @escaping, а DispatchQueue.main.async потребує.
  4. Реалізуй власний func orElse<T>(_ value: T?, _ fallback: @autoclosure () -> T) -> T.
