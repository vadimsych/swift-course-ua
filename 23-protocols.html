Протоколи

Протоколи — центральний інструмент абстракції в Swift. Вимоги до властивостей, методів і ініціалізаторів, протоколи як типи, делегування, розширення протоколів з реалізацією за замовчуванням, синтезовані й неявні відповідності, композиція, умовна відповідність.

У книзі: protocols

C#

Протокол — це інтерфейс, але потужніший. Головне, чого в C# немає: реалізацію за замовчуванням дописують окремо, через розширення, і протокол можна «приєднати» навіть до чужого типу, наприклад до String, не змінюючи його код.

Синтаксис

Swift
protocol Trackable {
    // вимоги
}

struct PurchaseEvent: Trackable, Codable { }

class AnalyticsScreen: UIViewController, Trackable { }   // суперклас — першим

Тип приймає (adopts) протокол, коли перелічує його в оголошенні, і відповідає (conforms) йому, коли реалізує всі вимоги.

Вимоги до властивостей

Протокол вказує ім'я, тип і чи властивість лише для читання ({ get }) або для читання й запису ({ get set }). Він не вказує, збережена вона чи обчислювана.

Swift
protocol Trackable {
    var eventName: String { get }
    var parameters: [String: String] { get }
}

struct ScreenView: Trackable {
    let screen: String
    var eventName: String { "screen_view" }                 // обчислювана
    var parameters: [String: String] { ["screen": screen] }
}
  • { get set } не можна задовольнити константою чи read-only обчислюваною властивістю.
  • { get } можна задовольнити будь-якою властивістю, зокрема й змінною var.
  • Вимоги до властивостей завжди пишуться через var.
  • Статичні вимоги позначаються static (у класах їх можна реалізувати як class).

Вимоги до методів

Метод описується як звичайна сигнатура без тіла. Значення параметрів за замовчуванням у протоколі задати не можна (але можна через розширення, див. нижче).

Swift
protocol PriceFormatter {
    func format(_ amount: Decimal, currency: String) -> String
    static func makeDefault() -> Self
}

Вимоги до мутуючих методів

Якщо метод змінює екземпляр value type, у протоколі його позначають mutating. Класи при реалізації mutating не пишуть.

Swift
protocol Resettable {
    mutating func reset()
}

struct Score: Resettable {
    var value = 0
    mutating func reset() { value = 0 }
}

final class Session: Resettable {
    var token: String?
    func reset() { token = nil }      // у класі без mutating
}

Вимоги до ініціалізаторів

Swift
protocol ConfigDecodable {
    init(config: [String: String])
}

Ініціалізатори протоколу в класах

Клас реалізує вимогу-ініціалізатор як required, щоб і всі підкласи гарантовано її мали:

Swift
class RemoteSetting: ConfigDecodable {
    let raw: [String: String]
    required init(config: [String: String]) { raw = config }
}

final-класу required не потрібен: підкласів у нього не буде. Якщо ініціалізатор одночасно перевизначає ініціалізатор суперкласу і реалізує протокол, пишуть required override.

Failable-вимоги

Протокол може вимагати init?. Його можна реалізувати як init? або як звичайний init. Вимогу init (non-failable) — лише звичайним або init!.

Протоколи лише із семантичними вимогами

Бувають протоколи без жодних методів — вони лише позначають властивість типу. Приклад — Sendable («можна передавати між потоками»). Свій такий протокол-маркер теж можна оголосити:

Swift
protocol AnalyticsSafe { }   // «цей тип не містить персональних даних»

Протоколи як типи

Протокол можна використовувати як тип, і є три способи:

Swift
// 1. Generic-обмеження: конкретний тип визначає викликач
func send<T: Trackable>(_ event: T) { }

// 2. Непрозорий тип: конкретний тип визначає реалізація
func makeEvent() -> some Trackable { ScreenView(screen: "home") }

// 3. Упакований (boxed) тип: будь-яке значення, що відповідає протоколу
var queue: [any Trackable] = []

Детально різниця між some і any — в уроці про непрозорі типи. Коротко: some/generics зберігають конкретний тип для компілятора і швидші, any дає гнучкість (різнорідні колекції) ціною динамічної диспетчеризації.

C#

any Trackable — це те, як у C# використовують інтерфейс як тип змінної: ITrackable e. Generics з обмеженням where T : ITrackable — це T: Trackable. У Swift ключове слово any робить «коробку» явною, бо вона має ціну.

Делегування

Делегування — патерн, де об'єкт передає частину відповідальності іншому об'єкту. Інтерфейс делегата описують протоколом:

Swift
protocol PurchaseFlowDelegate: AnyObject {
    func purchaseFlowDidStart(_ flow: PurchaseFlow)
    func purchaseFlow(_ flow: PurchaseFlow, didFinishWith productID: String)
    func purchaseFlowDidCancel(_ flow: PurchaseFlow)
}

final class PurchaseFlow {
    weak var delegate: PurchaseFlowDelegate?

    func buy(_ productID: String) {
        delegate?.purchaseFlowDidStart(self)
        // ... StoreKit ...
        delegate?.purchaseFlow(self, didFinishWith: productID)
    }
}

final class PaywallController: PurchaseFlowDelegate {
    let flow = PurchaseFlow()
    init() { flow.delegate = self }

    func purchaseFlowDidStart(_ flow: PurchaseFlow) { print("Спінер") }
    func purchaseFlow(_ flow: PurchaseFlow, didFinishWith productID: String) { print("Готово") }
    func purchaseFlowDidCancel(_ flow: PurchaseFlow) { }
}

Деталі:

  • Протокол делегата обмежують AnyObject, щоб властивість delegate могла бути weak і не створювала циклу посилань.
  • Першим параметром передають відправника — так один делегат може обслуговувати кілька об'єктів.
  • Протокол делегата можна оголосити вкладеним у тип, якому він служить: PurchaseFlow.Delegate.
C#

У C# ту саму роль зазвичай грають події (event Action<string> Finished). Делегат у Swift — це «одна підписка», яка задається інтерфейсом. У сучасному Swift-коді делегати часто замінюють замиканнями або async-функціями, але в UIKit вони всюди.

Відповідність через розширення

Відповідність протоколу можна додати існуючому типу, навіть якщо в тебе немає його вихідного коду. Усі екземпляри типу одразу отримують відповідність.

Swift
protocol DisplayPrice {
    var displayPrice: String { get }
}

extension Decimal: DisplayPrice {
    var displayPrice: String { "\(self) ₴" }
}

let p: Decimal = 149
p.displayPrice   // "149 ₴"

Умовна відповідність

Generic-тип може відповідати протоколу лише за певних умов — через where у розширенні:

Swift
extension Array: DisplayPrice where Element: DisplayPrice {
    var displayPrice: String {
        map(\.displayPrice).joined(separator: " + ")
    }
}

let cart: [Decimal] = [99, 49]
cart.displayPrice   // "99 ₴ + 49 ₴"

Масив [String] при цьому DisplayPrice не отримує.

Оголошення відповідності окремо

Якщо тип уже має все потрібне, достатньо оголосити відповідність порожнім розширенням:

Swift
struct Coupon {
    var displayPrice: String { "−20%" }
}
extension Coupon: DisplayPrice { }

Важливо: навіть якщо тип уже має всі потрібні члени, він відповідає протоколу лише після явного оголошення.

Синтезована реалізація

Для поширених протоколів компілятор сам генерує реалізацію, якщо ти оголосив відповідність:

  • Equatable — для структур, усі збережені властивості яких Equatable, і для enum, усі асоційовані значення яких Equatable (enum без асоційованих значень — завжди).
  • Hashable — за тими самими правилами з Hashable.
  • Comparable — для enum без сирих значень: порівняння за порядком оголошення варіантів, а асоційовані значення мають бути Comparable.
  • Codable — для структур, класів і enum з Codable-полями.
Swift
struct Money: Hashable, Codable {
    let amount: Decimal
    let currency: String
}

enum Tier: Comparable {
    case free, plus, pro
}

Money(amount: 1, currency: "USD") == Money(amount: 1, currency: "USD")   // true
Tier.free < Tier.pro                                                      // true

Синтез працює, лише якщо відповідність оголошено в тому самому файлі, що й сам тип (в оголошенні або в розширенні в цьому файлі).

C#

Схоже на те, що record генерує Equals і GetHashCode. У Swift це працює для звичайних структур і enum — достатньо дописати протокол.

Неявна відповідність

Для трьох протоколів компілятор виводить відповідність сам, без оголошення, якщо тип задовольняє їхні вимоги:

  • Copyable — значення можна копіювати (майже всі типи);
  • Sendable — для непублічних структур і enum, усі поля яких Sendable (урок про конкурентність);
  • BitwiseCopyable — значення копіюється простим копіюванням байтів (прості структури з числами).

Явне оголошення цих протоколів нічого не додає. Важливіше вміти відмовитися від неявної відповідності — тильдою перед протоколом. Наприклад, структура тримає сирий вказівник на буфер, який належить одному потоку рендерингу:

Swift
struct RenderScratch: ~Sendable {
    let buffer: UnsafeMutableRawPointer
    let size: Int
}

Після ~Sendable звичайну відповідність Sendable додати не вийде — лише @unchecked Sendable під твою відповідальність. Щоб заборонити і це:

Swift
@available(*, unavailable)
extension RenderScratch: Sendable { }

Окремо: розподілені актори (distributed actor) неявно відповідають Codable.

Колекції протокольних типів

Swift
let events: [any Trackable] = [
    ScreenView(screen: "home"),
    ScreenView(screen: "paywall"),
]

for e in events {
    print(e.eventName, e.parameters)   // доступні лише члени протоколу
}

Елемент має тип any Trackable, хоча реально там лежить ScreenView. До членів поза протоколом без приведення типу не дістатися.

Успадкування протоколів

Протокол може успадковувати інші протоколи й додавати свої вимоги:

Swift
protocol HasRemoteID {
    var id: String { get }
}

protocol RemoteEntity: HasRemoteID, Codable {
    static var endpoint: String { get }
}

struct Product: RemoteEntity {
    let id: String
    let title: String
    static var endpoint: String { "/products" }
}

Product мусить задовольнити вимоги всіх трьох протоколів (Codable синтезується).

Протоколи лише для класів

AnyObject у списку успадкування обмежує протокол класами (і акторами):

Swift
protocol ScreenRouter: AnyObject {
    func open(_ deepLink: String)
}

Таке обмеження потрібне, коли семантика передбачає reference type: делегати з weak, спільний змінюваний стан.

Протокол може також вимагати конкретний суперклас. Тоді прийняти його можуть лише підкласи цього класу, і в коді протоколу доступні члени суперкласу:

Swift
class BaseViewController { func showSpinner() { } }

protocol Loading: BaseViewController {
    func load() async
}

extension Loading {
    func reload() async {
        showSpinner()          // доступно: усі, хто Loading, — нащадки BaseViewController
        await load()
    }
}

Композиція протоколів

Коли потрібно значення, що відповідає кільком протоколам одночасно, їх з'єднують через &. До композиції можна додати й клас:

Swift
func sync(_ item: some HasRemoteID & Codable) { }

func register(_ screen: BaseViewController & Trackable) { }

typealias Persistable = HasRemoteID & Codable & Sendable

Композиція не створює нового протоколу, а лише описує тимчасовий набір вимог.

Перевірка відповідності

is, as? і as! працюють з протоколами так само, як з класами (урок про приведення типів):

Swift
let anything: [Any] = [ScreenView(screen: "a"), 42, "text"]

for item in anything {
    if let event = item as? any Trackable {
        print("Подія \(event.eventName)")
    }
}

Опціональні вимоги

У протоколах, позначених @objc, вимоги можна зробити необов'язковими через optional. Це механізм для сумісності з Objective-C (саме так влаштовані делегати UIKit на кшталт UITableViewDelegate):

Swift
@objc protocol GalleryDataSource {
    func numberOfImages() -> Int
    @objc optional func caption(at index: Int) -> String
}

final class Gallery {
    weak var dataSource: GalleryDataSource?

    func render() {
        let n = dataSource?.numberOfImages() ?? 0
        for i in 0..<n {
            let caption = dataSource?.caption?(at: i) ?? ""   // ? після імені методу
            print(i, caption)
        }
    }
}
  • Опціональна вимога стає опціональним значенням: метод — опціональною функцією.
  • Викликають її через опціональний ланцюжок: caption?(at:).
  • @objc-протоколи можуть приймати лише класи (будь-які), але не структури й enum.
  • Необов'язковою може бути й властивість: @objc optional var title: String { get }.
  • Навіть коли в ланцюжку два ? (опціональний делегат і опціональний метод), результат — один рівень опціональності.
Порада

У чистому Swift-коді опціональні вимоги замінюють реалізацією за замовчуванням у розширенні протоколу.

Розширення протоколів

Протокол можна розширити: додати методи, обчислювані властивості, ініціалізатори, сабскрипти з реалізацією. Тоді вони з'являються в усіх типів, що відповідають протоколу, без жодного коду в самих типах.

Swift
extension Trackable {
    var debugLine: String {
        "\(eventName) " + parameters.map { "\($0)=\($1)" }.sorted().joined(separator: " ")
    }
}

ScreenView(screen: "home").debugLine   // "screen_view screen=home"

Реалізація за замовчуванням

Розширення може реалізувати вимогу протоколу. Тип, що відповідає протоколу, може взяти цю реалізацію або дати свою:

Swift
protocol Trackable {
    var eventName: String { get }
    var parameters: [String: String] { get }
}

extension Trackable {
    var parameters: [String: String] { [:] }    // за замовчуванням — без параметрів
}

struct AppOpen: Trackable {
    var eventName: String { "app_open" }        // parameters не потрібні
}
Пастка

Якщо метод є лише в розширенні протоколу, а не в його вимогах, тип не може його «перевизначити»: при виклику через any Trackable спрацює версія з розширення. Хочеш перевизначення — додай метод у вимоги протоколу.

Обмеження в розширеннях протоколів

Розширення можна обмежити умовою where:

Swift
extension Collection where Element: Trackable {
    func sendAll() {
        forEach { print("send", $0.eventName) }
    }
}

extension Collection where Element: Numeric & Comparable {
    func spread() -> Element? {
        guard let lo = self.min(), let hi = self.max() else { return nil }
        return hi - lo
    }
}

[ScreenView(screen: "a")].sendAll()
[120, 90, 300].spread()     // 210

Якщо підходить кілька обмежених реалізацій, Swift бере найспецифічнішу.

Перевір себе

Обери відповідь — одразу побачиш, чи правильно, і пояснення.

1. Клас Screen успадковує BaseScreen і приймає протокол Trackable. Яке оголошення правильне?

У списку успадкування суперклас пишуть першим, а протоколи — після нього.

2. Чому тут помилка компіляції?

Swift
protocol Counter {
    var value: Int { get set }
}

struct Clicks: Counter {
    let value: Int
}

print(Clicks(value: 1).value)

{ get set } вимагає, щоб властивість можна було змінювати. Константа let цього не дає.

3. Що з цього не можна написати у вимозі методу всередині протоколу?

Значення за замовчуванням у самому протоколі задати не можна. Це роблять через розширення протоколу.

4. Чому тут помилка компіляції?

Swift
protocol Resettable {
    func reset()
}

struct Score: Resettable {
    var value = 5
    mutating func reset() { value = 0 }
}

var s = Score()
s.reset()
print(s.value)

Якщо метод має змінювати value type, вимогу треба позначити mutating у протоколі.

5. Протокол вимагає init?(raw: String). Як тип може реалізувати цю вимогу?

Failable-вимогу можна задовольнити і failable, і звичайним ініціалізатором.

6. Чому тут помилка компіляції?

Swift
protocol Configurable {
    init(name: String)
}

class Setting: Configurable {
    let name: String
    init(name: String) { self.name = name }
}

print(Setting(name: "dark").name)

required гарантує, що ініціалізатор матимуть і всі підкласи. Для final-класу він не потрібен.

7. Навіщо оголошувати протокол без жодної вимоги, як protocol AnalyticsSafe { }?

Такий протокол — маркер зі змістом. Приклад зі стандартної бібліотеки — Sendable.

8. Який запис дозволяє тримати в одному масиві значення різних типів, що відповідають Trackable?

any — упакований тип: кожен елемент може мати свій конкретний тип. some і generics фіксують один тип.

9. Навіщо протокол делегата обмежують AnyObject?

weak можливий лише для посилальних типів. AnyObject гарантує, що делегат — клас.

10. Що надрукує цей код?

Swift
protocol Labeled {
    var label: String { get }
}

extension Int: Labeled {
    var label: String { "\(self) шт." }
}

print(5.label)

Розширення додає відповідність навіть стандартному типу Int, і всі його значення одразу її отримують.

11. Чому тут помилка компіляції?

Swift
protocol Labeled {
    var label: String { get }
}

extension Int: Labeled {
    var label: String { "#\(self)" }
}

extension Array: Labeled where Element: Labeled {
    var label: String { map(\.label).joined(separator: ", ") }
}

print(["a", "b"].label)

Масив відповідає Labeled лише тоді, коли його елементи відповідають Labeled. Для Int це спрацювало б.

12. Яке твердження про синтезовану реалізацію неправильне?

Comparable синтезується лише для enum без сирих значень, і порівнюють за порядком оголошення.

13. Відповідність якому протоколу компілятор не виводить сам, без оголошення?

Неявно виводяться Copyable, Sendable і BitwiseCopyable. Equatable треба оголосити, і тоді його синтезують.

14. Чому тут помилка компіляції?

Swift
protocol Named {
    var name: String { get }
}

struct ScreenView: Named {
    let screen: String
    var name: String { "screen_view" }
}

let items: [any Named] = [ScreenView(screen: "home")]
for item in items {
    print(item.screen)
}

Через any Named доступні лише члени протоколу. До screen дістатися можна лише після приведення типу.

15. Що надрукує цей код?

Swift
protocol HasID {
    var id: Int { get }
}

protocol Entity: HasID {
    var title: String { get }
}

struct Item: Entity {
    let id: Int
    let title: String
}

func show(_ x: some Entity) {
    print(x.id, x.title)
}

show(Item(id: 7, title: "box"))

Entity успадковує вимоги HasID, тож у функції доступні і id, і title.

16. Чому тут помилка компіляції?

Swift
protocol ScreenRouter: AnyObject {
    func open(_ link: String)
}

struct Router: ScreenRouter {
    func open(_ link: String) { print(link) }
}

Router().open("home")

AnyObject у списку успадкування дозволяє приймати протокол лише класам (і акторам).

17. Що означає параметр _ item: some HasID & Codable?

& з'єднує вимоги: тип мусить задовольняти обидва протоколи. Нового протоколу композиція не створює.

18. Що надрукує цей код?

Swift
protocol Named {
    var name: String { get }
}

struct Point: Named { var name: String { "pt" } }
struct Box: Named { var name: String { "box" } }

let items: [Any] = [Point(), 42, "text", Box()]
for item in items {
    if let named = item as? any Named {
        print(named.name)
    }
}

as? any Named успішний лише для значень, що відповідають протоколу. 42 і "text" пропускаються.

19. Яке твердження про опціональні вимоги (optional) неправильне?

@objc-протоколи можуть приймати лише класи. Структури й enum — ні.

20. Що надрукує цей код?

Swift
protocol Named {
    var name: String { get }
}

extension Named {
    var greeting: String { "Hi, \(name)" }
}

struct User: Named {
    let name: String
}

print(User(name: "Ann").greeting)

Член із розширення протоколу з'являється в усіх типів, що йому відповідають, без коду в самих типах.

21. Що надрукує цей код?

Swift
protocol Greeter {
    func hello()
}

extension Greeter {
    func hello() { print("default hello") }
    func bye() { print("default bye") }
}

struct Cat: Greeter {
    func hello() { print("cat hello") }
    func bye() { print("cat bye") }
}

let g: any Greeter = Cat()
g.hello()
g.bye()

hello є вимогою протоколу, тож викликається версія Cat. bye є лише в розширенні, і через any Greeter спрацьовує версія з розширення.

22. Що надрукує цей код?

Swift
extension Collection where Element: Numeric & Comparable {
    func spread() -> Element? {
        guard let lo = self.min(), let hi = self.max() else { return nil }
        return hi - lo
    }
}

print([120, 90, 300].spread())

Метод з обмеженого розширення доступний для [Int], але повертає Element?, тож print показує Optional(210).
