Обробка помилок

Як Swift описує, кидає й обробляє помилки: throws, try, do-catch, try?, try!, типізовані помилки (throws(E)) і defer. Головна відмінність від C# — помилки є частиною сигнатури, а не прихованими винятками.

У книзі: errorhandling

Опис і кидання помилок

Помилка — значення будь-якого типу, що реалізує протокол Error. Найзручніше — enum:

Swift
enum StoreError: Error {
    case productNotFound(id: String)
    case paymentNotAllowed
    case network(code: Int)
}

throw StoreError.productNotFound(id: "pro_monthly")

Вимог у Error немає — відповідність лише дозволяє кидати значення типу. Щоб помилка мала людське повідомлення, реалізують ще LocalizedError (errorDescription) або CustomStringConvertible.

C#

Винятки в C# — класи, що успадковуються від Exception, зі стеком викликів. У Swift помилки легковагові: enum або struct без стека, а «кидання» — це по суті повернення значення через окремий канал. Це не дорого, і помилки нормально використовувати для очікуваних збоїв.

Обробка помилок

Swift вимагає явно позначати місця, де може виникнути помилка: ключове слово try перед викликом. Читаючи код, одразу видно, які рядки можуть перервати виконання.

Є чотири способи обробити помилку:

  1. передати її далі викликачу;
  2. обробити в do-catch;
  3. перетворити на опціонал (try?);
  4. стверджувати, що помилки не буде (try!).

Передача далі: throwing-функції

Функція, що може кинути помилку, позначається throws перед ->:

Swift
struct Product { let id: String; let price: Decimal }

final class Store {
    private var catalog: [String: Product] = [:]
    var canPay = true

    func product(id: String) throws -> Product {
        guard let p = catalog[id] else {
            throw StoreError.productNotFound(id: id)
        }
        return p
    }

    func buy(id: String) throws -> Decimal {
        guard canPay else { throw StoreError.paymentNotAllowed }
        let p = try product(id: id)     // помилка піде далі автоматично
        return p.price
    }
}

Якщо функцію не позначено throws, компілятор вимагає, щоб усі помилки, які виникають у ній, були оброблені всередині — передати їх викликачу вона не може.

Ініціалізатори теж можуть бути throws — тоді невдала ініціалізація повідомляє причину, а не просто nil, як init?:

Swift
struct Receipt {
    let data: Data
    init(fileAt url: URL) throws {
        data = try Data(contentsOf: url)          // помилка читання піде викликачу
        guard !data.isEmpty else { throw StoreError.network(code: 0) }
    }
}

let receipt = try Receipt(fileAt: receiptURL)

do-catch

Swift
let store = Store()

do {
    let price = try store.buy(id: "pro_yearly")
    print("Сплачено \(price)")
} catch StoreError.productNotFound(let id) {
    print("Немає продукту \(id)")
} catch StoreError.network(let code) where code >= 500 {
    print("Сервер недоступний")
} catch is StoreError {
    print("Інша помилка магазину")
} catch {
    print("Невідома помилка: \(error)")   // error — неявна константа
}
  • Після catch пишуть зразок, як у case всередині switch, разом із where.
  • catch без зразка ловить усе і надає константу error.
  • Гілки не обов'язково вичерпні. Якщо помилку не зловлено, вона піде далі — тоді функція навколо мусить бути throws.

Кілька зразків в одній гілці — через кому:

Swift
} catch StoreError.paymentNotAllowed, StoreError.network {
    showRetry()
}

Перетворення на опціонал

try? повертає nil, якщо виникла помилка, і відкидає саму помилку. Зручно, коли конкретна причина неважлива, а важливо лише «вийшло чи ні»:

Swift
let savedLevel = (try? storage.loadInt(forKey: "level")) ?? 1

let avatars = urls.compactMap { try? Data(contentsOf: $0) }   // пропускаємо ті, що не завантажились

Якщо функція вже повертає опціонал, try? не додає зайвого рівня: результат T?, а не T??.

Вимкнення поширення

try! стверджує, що помилки не буде. Якщо помилка таки виникне — крах. Він доречний лише там, де помилка означає баг у самому застосунку, а не зовнішній збій:

Swift
// регулярний вираз написаний у коді: якщо він некоректний — це помилка програміста
let promoPattern = try! Regex("^[A-Z]{4}-\\d{4}$")
C#

try? — як try { x = F(); } catch { x = null; } одним словом. try! — як виклик без catch з гарантованим падінням застосунку. Аналога finally немає, його роль виконує defer.

Тип помилки

За замовчуванням throws означає «може кинути будь-яку помилку», тобто any Error. Можна вказати конкретний тип — типізовані помилки:

Swift
func validate(_ code: String) throws(PromoError) -> Int {
    guard code.count == 8 else { throw .wrongLength }
    return 10
}

enum PromoError: Error {
    case wrongLength
    case expired
}

do {
    let discount = try validate("ABC")
    print(discount)
} catch {
    // error тут має тип PromoError, а не any Error
    switch error {
    case .wrongLength: print("Код має 8 символів")
    case .expired: print("Код протерміновано")
    }
}
  • throws(E) дозволяє кидати лише E.
  • У do-catch можна явно вказати тип: do throws(PromoError) { ... }.
  • throws(Never) — функція, яка не кидає взагалі, а throws(any Error) — те саме, що throws.
  • Generic-код може бути throws(E) з параметром E, і тоді тип помилки «прокидається» через функції вищого порядку.

Корисні деталі:

  • Якщо тип помилки відомий, у throw можна писати скорочено: throw .wrongLength.
  • do-блок, у якому всі try кидають той самий конкретний тип, сам вважається throws(ЦейТип) — тому в catch вище error має тип PromoError. Якщо типи різні, виводиться any Error. Явно задати тип можна через do throws(PromoError) { }, а відмовитися від виведення — через do throws(any Error) { }.
  • Помилка, що дійшла до верхнього рівня програми й не оброблена, зупиняє програму.

Типізовані помилки варто брати, коли набір помилок закритий і стабільний (внутрішній код модуля), коли generic-код лише передає помилки з переданих замикань, або коли важлива відсутність виділення пам'яті. Для публічних API бібліотек частіше лишають звичайний throws, щоб у майбутньому можна було додати нові види помилок без зламу сумісності.

Swift 6

Типізовані помилки з'явилися у Swift 6. У старому коді ти побачиш Result<Success, Failure> для тих самих цілей.

Дії при виході: defer

defer виконує код при виході з області видимості — і при return, і при кинутій помилці:

Swift
func exportReport() throws {
    let file = try openFile("report.csv")
    defer { file.close() }               // закриється в будь-якому разі

    try file.write(header)
    for row in rows {
        try file.write(row)              // помилка тут — file.close() все одно виконається
    }
}

Кілька defer виконуються у зворотному порядку. Усередині defer не можна виходити з блоку (return, break, throw). defer працює й без помилок (урок про керування потоком).

Rethrows

Функція, яка приймає throwing-замикання і кидає помилки лише з нього, позначається rethrows. Якщо передати не-throwing замикання, try при виклику не потрібен:

Swift
func retry<T>(times: Int, _ action: () throws -> T) rethrows -> T {
    precondition(times >= 1, "Потрібна щонайменше одна спроба")
    for _ in 1..<times {
        if let value = try? action() { return value }
    }
    return try action()
}

let n = retry(times: 3) { 42 }                 // без try
let d = try retry(times: 3) { try download() } // з try

Так влаштовані filter, contains(where:) і багато інших методів колекцій. У новіших частинах стандартної бібліотеки, як-от map, замість rethrows використовують generic типізовану помилку throws(E): тоді тип помилки із замикання зберігається.

Перевір себе

Обери відповідь — одразу побачиш, чи правильно, і пояснення.

1. Що потрібно, щоб кинути помилку з функції?

Помилка — будь-який тип, що відповідає Error (найчастіше enum). Функція без throws кинути її назовні не може.

2. Що повертає try? load(), якщо load() кинула помилку?

try? перетворює результат на опціонал і відкидає помилку.

3. Що станеться з try! load(), якщо load() кинула помилку?

try! стверджує, що помилки не буде. Якщо вона є — крах. Доречно лише там, де помилка означає баг у коді.

4. Яке твердження неправильне?

Помилки в Swift — легкі значення (enum, struct) без стека. «Кидання» — це по суті повернення через окремий канал, і воно дешеве.

5. Що надрукує цей код?

Swift
enum E: Error { case bad }
func run() throws {
    defer { print("cleanup") }
    throw E.bad
}
do { try run() } catch { print("caught") }

defer спрацьовує при виході з функції, навіть через помилку, — тобто до того, як помилку зловлять зовні.

Практика
  1. Опиши enum ReceiptError: Error для валідації чека (немає підпису, неправильний bundle ID, протермінована підписка) і функцію validate(_:) throws(ReceiptError).
  2. Обробляй помилки цієї функції в do-catch з окремими гілками для кожного варіанта і з where.
  3. Напиши функцію, що послідовно пробує три джерела конфігурації (кеш, мережа, вбудований файл) через try?.
  4. Реалізуй LocalizedError для своєї помилки й виведи error.localizedDescription.
