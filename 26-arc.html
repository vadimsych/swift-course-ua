Автоматичний підрахунок посилань (ARC)

Як Swift керує пам'яттю об'єктів без збирача сміття, звідки беруться цикли сильних посилань у реальному iOS-коді і як їх розривати через weak, unowned і capture lists.

У книзі: automaticreferencecounting

Як працює ARC

Кожен об'єкт класу має лічильник: скільки змінних і властивостей на нього посилаються. Компілятор сам збільшує й зменшує його в потрібних місцях. Коли лічильник стає нулем, об'єкт одразу звільняється, а перед цим викликається deinit. Структур і enum це не стосується — вони копіюються як значення.

  • Рішення, де рахувати, ухвалює компілятор, а сам підрахунок відбувається в рантаймі: атомарні операції над лічильником.
  • Звільнення детерміноване: після останнього використання останнього сильного посилання, без окремого збирача.
  • Структури й enum лічильника не мають: вони копіюються як значення.
ARC (Swift) GC (.NET, Unity)
Коли звільняється одразу, коли лічильник = 0 колись, коли запуститься збирач
Паузи немає stop-the-world є (GC spikes)
Ціна невелика на кожне копіювання посилання зосереджена в момент збирання
Цикли посилань не збираються збираються, бо GC обходить граф від коренів
Деструктор deinit, передбачувано finalizer, недетерміновано
C#

Для Unity-розробника головне: GC spikes не буде, зате відповідальність за цикли посилань — на тобі. Збирач сміття прибрав би два об'єкти, які тримають лише один одного, а ARC — ні.

Як побачити ARC у роботі

Найпростіший інструмент — print у deinit. Візьмемо екран, що живе, поки його показує навігація:

Swift
final class CheckoutScreen {
    let orderID: String
    init(orderID: String) { self.orderID = orderID }
    deinit { print("CheckoutScreen \(orderID) звільнено") }
}

final class Navigator {
    var stack: [CheckoutScreen] = []
    func push(_ s: CheckoutScreen) { stack.append(s) }
    func pop() { stack.removeLast() }
}

let nav = Navigator()
nav.push(CheckoutScreen(orderID: "A-17"))   // сильне посилання тримає масив stack
nav.pop()                                   // останнє посилання зникло → deinit

Екран ніхто не «видаляв» явно: ARC звільнив його, щойно масив перестав на нього посилатися. Якщо після pop() повідомлення немає — значить, хтось іще тримає екран. Найчастіше цей «хтось» — цикл посилань.

Цикли сильних посилань між об'єктами

Типова ситуація в iOS: контролер володіє ViewModel, а ViewModel повідомляє контролера про зміни через посилання назад.

Swift
final class ProfileViewModel {
    var view: ProfileController?          // ⚠️ сильне посилання назад
    func refresh() { view?.render() }
}

final class ProfileController {
    let viewModel = ProfileViewModel()
    init() { viewModel.view = self }
    func render() { }
    deinit { print("ProfileController звільнено") }
}

var screen: ProfileController? = ProfileController()
screen = nil      // deinit не викличеться
ProfileController ──viewModel──▶ ProfileViewModel
        ▲                               │
        └──────────── view ─────────────┘

Змінна screen зникла, але контролер тримає ViewModel, а ViewModel — контролер. Обидва лічильники більші за нуль, і пам'ять не звільниться ніколи.

Розрив циклів між об'єктами

Є два види посилань, що не збільшують лічильник: weak і unowned.

  • weak — коли інший об'єкт може зникнути раніше або його життя не залежить від твого;
  • unowned — коли інший об'єкт гарантовано живе стільки ж або довше.

Слабкі посилання

weak завжди var і завжди опціональне: коли об'єкт звільняється, ARC автоматично записує в слабке посилання nil (спостерігачі властивості при цьому не викликаються).

Swift
final class ProfileViewModel {
    weak var view: ProfileController?     // не утримує контролер
    func refresh() { view?.render() }
}

Правило напрямку: власник тримає сильно, зворотне посилання — weak. Контролер володіє ViewModel, тож саме посилання ViewModel → контролер стає слабким. Так влаштовані всі делегати в UIKit.

Пам'ятай, що weak впливає на лічильник того, на кого вказує посилання. Об'єкт живе, доки на нього є хоча б одне сильне посилання, а слабкі лише «спостерігають».

Порада

weak не підходить для кешів: об'єкт зникне, щойно на нього не лишиться сильних посилань, навіть якщо пам'яті вдосталь. Для кешів використовують NSCache або власне сховище з явним витісненням.

Безвласницькі посилання

unowned теж не утримує об'єкт, але й не стає nil — це не опціонал. Якщо звернутися до нього після звільнення об'єкта, буде крах. Підходить для зв'язку «дитина → батько», де дитина не живе довше за батька:

Swift
final class Form {
    private(set) var fields: [Field] = []
    var isValid: Bool { fields.allSatisfy(\.isValid) }

    func addField(placeholder: String) {
        fields.append(Field(form: self, placeholder: placeholder))
    }
}

final class Field {
    unowned let form: Form          // поле не існує без форми
    let placeholder: String
    var text = ""
    var isValid: Bool { !text.isEmpty }

    init(form: Form, placeholder: String) {
        self.form = form
        self.placeholder = placeholder
    }

    func didEdit() {
        print("Форма валідна:", form.isValid)   // без розгортання опціоналу
    }
}

Форма тримає поля сильно (через масив), поля посилаються на форму через unowned. Поле не може пережити форму, бо живе лише в її масиві.

Існують також:

  • опціональне unowned (unowned var selected: Field?) — можна присвоїти nil вручну, але саме воно не обнулиться;
  • unowned(unsafe) — вимикає перевірку в рантаймі: після звільнення об'єкта звернення не впаде контрольовано, а прочитає звільнену пам'ять. Застосовують лише для оптимізації в дуже гарячому коді.
Пастка

unowned — це обіцянка компілятору. Якщо помилишся з часом життя, отримаєш крах у рантаймі. Якщо є хоч найменший сумнів — бери weak.

Коли обидва посилання мають бути не-опціональними

Буває, що обидва об'єкти обов'язково існують разом: наприклад, ігровий світ створює свій фізичний рушій, і рушію потрібен світ. Найчистіше рішення — створювати залежний об'єкт ліниво: у lazy-властивості вже можна використовувати self.

Swift
final class World {
    let name: String
    lazy var physics = PhysicsEngine(world: self)   // створюється при першому зверненні
    init(name: String) { self.name = name }
}

final class PhysicsEngine {
    unowned let world: World
    init(world: World) { self.world = world }
}

let w = World(name: "Arena")
print(w.physics.world.name)     // жодних опціоналів
Пастка

unowned тут чесно попереджає про помилки часу життя. Вираз World(name: "Arena").physics.world.name впаде: тимчасовий World звільняється одразу після створення physics, і рушій лишається з посиланням на знищений об'єкт. У прикладі вище світ живе, бо його тримає константа w.

Старіший варіант того самого — властивість типу PhysicsEngine! (неявно розгорнутий опціонал), яку присвоюють у init після ініціалізації решти властивостей. Його часто можна побачити в UIKit-коді.

Цикли сильних посилань через замикання

Замикання — теж reference type, і воно сильно захоплює все, що використовує, включно з self. Якщо об'єкт (прямо чи через інші об'єкти) зберігає замикання, а замикання захоплює об'єкт, виникає цикл. На практиці це найчастіше джерело витоків:

Swift
final class SearchViewModel {
    var results: [String] = []
    private var onQueryChange: ((String) -> Void)?

    init() {
        onQueryChange = { query in
            self.results = ["\(query)…"]     // ⚠️ замикання тримає self
        }
    }
    deinit { print("SearchViewModel звільнено") }
}
SearchViewModel ──onQueryChange──▶ [замикання]
       ▲                                │
       └───────────── self ─────────────┘

Те саме виникає з таймерами, підписками Combine, колбеками мережевих клієнтів, NotificationCenter з блоком і довгими Task.

Тому в escaping-замиканнях класу Swift вимагає писати self. явно — щоб ти помітив, що замикання тримає об'єкт.

Розрив циклів у замиканнях

Capture list

Перед параметрами замикання в квадратних дужках пишуть список захоплення — як саме захопити кожне значення:

Swift
init() {
    onQueryChange = { [weak self] query in
        guard let self else { return }
        self.results = ["\(query)…"]
    }
}

// захоплення значення, а не змінної — копія в момент створення
let pageSize = 20
loader.onNextPage = { [pageSize] page in fetch(page, size: pageSize) }

Значення зі списку обчислюються в момент створення замикання.

weak чи unowned у замиканнях

  • [weak self] — якщо замикання може пережити об'єкт: асинхронні колбеки, таймери, підписки, обробники подій. Усередині self — опціонал.
  • [unowned self] — якщо замикання і об'єкт гарантовано звільняються разом і замикання ніколи не викликається після звільнення self. Наприклад, замикання зберігається лише у власній властивості об'єкта й викликається лише його ж методами.

guard let self else { return } на початку замикання створює тимчасове сильне посилання до кінця його виконання — так об'єкт не зникне посеред роботи.

Пастка

У Task { [weak self] in ... } з нескінченним for await не роби guard let self перед циклом: сильне посилання житиме весь час, і weak нічого не дасть. Перевіряй self усередині циклу на кожній ітерації або скасовуй задачу.

Порада

Шукати витоки зручно в Xcode → Debug Memory Graph: об'єкти, що мали б зникнути, і стрілки сильних посилань між ними видно наочно. Простий тест — print у deinit екрана: закрив екран, а повідомлення немає — є цикл.

Перевір себе

Обери відповідь — одразу побачиш, чи правильно, і пояснення.

1. Яке твердження про ARC неправильне?

ARC дивиться лише на лічильники й не обходить граф об'єктів. Цикл сильних посилань сам не звільниться.

2. Що надрукує цей код?

Swift
final class Session {
    init() { print("init") }
    deinit { print("deinit") }
}

func run() {
    var list: [Session] = [Session()]
    list.removeAll()
    print("кінець")
}
run()

Масив тримав єдине сильне посилання. Після removeAll() лічильник став нулем, і deinit викликався одразу.

3. Що надрукує цей код?

Swift
final class Screen {
    let id: Int
    init(id: Int) { self.id = id }
    deinit { print("звільнено \(id)") }
}

func run() {
    var a: Screen? = Screen(id: 1)
    let b = a
    a = nil
    print("після a = nil")
    print(b?.id ?? 0)
}
run()

Після a = nil об'єкт ще тримає b. Звільнення відбувається лише після останнього використання останнього сильного посилання.

4. Що надрукує цей код?

Swift
final class A { var b: B?; deinit { print("A звільнено") } }
final class B { var a: A?; deinit { print("B звільнено") } }

func run() {
    var a: A? = A()
    var b: B? = B()
    a?.b = b
    b?.a = a
    a = nil
    b = nil
    print("кінець")
}
run()

A і B сильно тримають один одного. Після обнулення змінних обидва лічильники більші за нуль, тож deinit не викликається.

5. Контролер володіє своєю ViewModel, а ViewModel повідомляє контролер про зміни. Як розірвати цикл?

Власник тримає сильно, а зворотне посилання робиться weak. Якщо обидва weak, ViewModel ніхто не триматиме.

6. Що надрукує цей код?

Swift
final class Owner { deinit { print("Owner звільнено") } }

func run() {
    var owner: Owner? = Owner()
    weak var ref = owner
    owner = nil
    print(ref == nil)
}
run()

weak не збільшує лічильник. Коли зникло єдине сильне посилання, об'єкт звільнився, а ARC записав у ref значення nil.

7. Чому тут помилка компіляції?

Swift
final class Owner {}

final class Holder {
    weak var owner: Owner
    init(owner: Owner) { self.owner = owner }
}

ARC обнуляє слабке посилання, коли об'єкт звільняється. Тому тип має бути опціональним.

8. Що станеться при запуску цього коду?

Swift
final class Parent { let name = "P" }

final class Child {
    unowned let parent: Parent
    init(parent: Parent) { self.parent = parent }
}

func run() {
    var p: Parent? = Parent()
    let c = Child(parent: p!)
    p = nil
    print(c.parent.name)
}
run()

unowned не утримує об'єкт і не стає nil. Після звільнення Parent звернення до parent призводить до краху.

9. Коли доречно брати unowned замість weak?

unowned — обіцянка, що об'єкт переживе посилання. Якщо є сумнів, бери weak.

10. Чому в lazy var physics = PhysicsEngine(world: self) можна використати self?

lazy відкладає створення до першого звернення. На той момент об'єкт повністю ініціалізований.

11. Що надрукує цей код?

Swift
final class Search {
    var results: [String] = []
    var onChange: ((String) -> Void)?

    init() {
        onChange = { query in
            self.results = [query]
        }
    }
    deinit { print("Search звільнено") }
}

func run() {
    var s: Search? = Search()
    s = nil
    print("кінець")
}
run()

Об'єкт зберігає замикання, а замикання сильно захоплює self. Виник цикл, тож deinit не викликається.

12. Навіщо Swift вимагає писати self. явно в escaping-замиканнях класу?

Явний self. нагадує, що замикання тримає об'єкт сильно і може утворити цикл.

13. Що надрукує цей код?

Swift
func run() {
    var count = 1
    let a = { [count] in print(count) }
    let b = { print(count) }
    count = 5
    a()
    b()
}
run()

Значення зі списку захоплення копіюються в момент створення замикання. Замикання без списку бачить поточне значення змінної.

14. Яке твердження неправильне?

guard let self перед нескінченним циклом триматиме об'єкт увесь час, і weak нічого не дасть. Перевіряй self на кожній ітерації.

Практика
  1. Відтвори цикл між контролером і ViewModel з цього уроку, переконайся через deinit, що об'єкти не звільняються, а потім виправ його через weak.
  2. Зроби клас, що запускає Timer.scheduledTimer(withTimeInterval:repeats:block:) і в блоці звертається до self. Перевір дві речі: чи звільняється об'єкт з [weak self] і чи продовжує після цього спрацьовувати сам таймер. Чому без invalidate() таймер живе далі?
  3. Зроби пару Playlist і Track, де трек знає свій плейлист через unowned, а плейлист має unowned var nowPlaying: Track?.
  4. Знайди в будь-якому своєму Swift-коді замикання, що зберігаються у властивостях, і перевір, чи немає циклів.
